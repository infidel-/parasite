# Repository Guidelines

## Build targets (root Makefile)
- `make` / `make game-debug`: `cd src && make electron`
- `make testmod`: `cd examples/testmod/ && make`
- `make main`: `cd electron && make`

## Driving the running game (CDP / smoke-test)
- The Electron app runs with `--remote-debugging-port=9300`; the `chrome-devtools` MCP is wired to it (`172.18.208.1:9300`, WSL→Windows host). After `make reload`, drive/inspect the live app with `mcp__chrome-devtools__*` (`list_pages` → `evaluate_script` / `click` / `list_console_messages`) to smoke-test clicks and catch runtime exceptions.
- `list_pages` shows both the game (`file:.../app.html`) and, if open, DevTools — match `file:` + `app.html`. First MCP call may transient-fail; retry once.
- **FIRST call of every CDP session is `select_page` with `bringToFront: true`** — `list_pages` for the id, then `select_page({ pageId, bringToFront: true })`, which issues `Page.bringToFront`. `bringToFront` is optional and defaults to OFF, so it never happens unless asked for. Minimise the game or bury it under the terminal and Chromium stops compositing: `requestAnimationFrame` never fires and anything awaiting a frame never resolves, so `evaluate_script` and `take_screenshot` hang for the MCP's full 180s `protocolTimeout` (not configurable — there is no CLI flag) while `list_pages`, a browser-level call, still answers cheerfully. Browser-level call works + page-level call hangs = **hidden window**. One call up front removes the whole class of hang. Borrowed from `~/orwell/cdp/probe.mjs`, which does it before every eval.
- **`backgroundThrottling: false` is already set** (`electron/MainElectron.hx`, and present in the packaged build). It does NOT cover this: it relaxes timer throttling for a *visible-but-backgrounded* page, while a minimised or occluded window stops compositing outright. Do not reach for it again.
- **A raised CDP target is still not a focused OS window.** After `bringToFront` the HUD can still read **1 FPS** — enough to screenshot and evaluate, nowhere near enough to measure. Check the topbar fps before trusting any timing (see the measurement rules in `docs/3d-render.md`).

## Debug surface (what CDP `evaluate_script` can actually reach)
- **ASK before extending the debug surface.** If a new/extended hook (`window.__*`, a debug key, a HUD readout, a trace) looks worth adding — say what it would expose and why, and ask. Do not add one unprompted: these are permanent instrumentation in shipped game code, they accrete, and the value is a judgement call the user makes. Using or reading the EXISTING hooks below needs no ask.
- **ALWAYS consider making a debug hook PERMANENT, not throwaway.** When a task needs a one-off hook to inspect live state, default to proposing it as a permanent, documented hook (added to this list) rather than a temporary one you rip out after — if it was useful once it is likely useful again, and re-adding it each time is wasted work. Ask (per the rule above), but frame it as permanent.
- **`window.parasiteHx` is the Haxe class registry (`$hxClasses`) — STATICS ONLY.** Do not burn turns BFS-ing `window`/`Main`/`GameScene` for the scene graph; it is not there. **The one instance a static DOES hand over is the whole game model: `parasiteHx['game.Game'].inst` is the live `Game`**, and from it `inst.area` reaches every `AreaObject` in the area — which is how a door was opened from CDP to check its swing without walking the player to it. Two gotchas: `area.getObjects()` returns a Haxe ITERATOR, not an array (`while (it.hasNext()) it.next()`, never `for...of`), and writing a field directly bypasses the object's own setter, so restore what you changed rather than leaving the save inconsistent. **The RENDER side hangs off that same instance and needs no hook: `game.scene.view3d` IS the live `render.View`** — `.scene` (the whole three graph, `traverse` it), `.camera`, `.renderer`, `.composer`, `.rig`, `.setRenderScale(s)`, and `.perf`, whose `lastGpuMs` is the real timer-query readout once `parasiteHx['render.Actors'].DEBUG_PERF = true`. That is a complete render A/B harness from CDP with nothing added to shipped code: walk the scene for the `InstancedMesh` batches, flip `visible`/`castShadow` or swap a material, and take the MEDIAN of `perf.lastGpuMs` over ~30 frames per phase (see the weak-GPU rules below). Two duties: **restore everything you touched** (materials, `visible`, `castShadow`, render scale, `DEBUG_PERF` — and any static you monkey-patched, e.g. a no-op `Models.cull` to freeze instance culling), and remember a reload wipes it all anyway. Anything the `View` does not own still wants a hook below (`untyped js.Browser.window.__x = {...}` from the class that owns the data). Pure functions ARE reachable: e.g. `parasiteHx['citygen.CityGen'].generate(seed)` regenerates any city headlessly, which is how you test city-layout claims across many seeds without loading a save. **Static STATE is reachable too, and that is the cheap way to verify a whole subsystem** — `parasiteHx['render.world.VisionMask']` hands over the live LOS mask's `canvas`, `wallLayer` and `opt`, so "is the shadow where the polygon says it is" is a `getImageData` and not a screenshot. It also runs the other way: calling `VisionMask.attach(SewerStyle.MASK, m.w, m.h, ...)` on a `SewerModel.demo()` regression-tests the tunnel branch without travelling to a tunnel. That CLOBBERS the live area's statics — reload afterwards.
- **`window.__check`** (`render/world/Check.hx`) — post-gen checklist: `pass`, `fails`, `windowless`, `doorless`, `noBackDoor`, `blank`, `counts`, `goto(i)`. Attached on world gen. Red badge in the topbar mirrors `fails`.
- **`window.__occ`** (`render/Occlusion.hx`) — building-fade bucketing: `stats()` → `{buildings, meshes, skipped}`; `skipped()` → `[{cls, size:[x,z]}]`, the meshes `pick()` left unbucketed, so they never fade. Expect ~9: the city-wide ground/kerb/markings, roof contact shadows, lamp posts and lamp cones all sit at `position (0,0,0)` (world-baked verts, or spread living in `instanceMatrix`) and are rejected by `pick()`'s size guard — without it they'd bucket into whatever building covers the grid centre and go see-through with it. A per-building mesh showing up here is a bug: it means it stopped fading. Attached on area build.
- **`window.__dbg`** (`render/Debug.hx`) — `count('door-cover-')`, `find('door-cover-stone')` → `[{cls,type,tris,pos,size}]`, `cam(cls, dist, up)` → frame the free-cam on the first match. **Gated: only exists after entering street-debug mode (backtick) once** — `attachTools()` builds it lazily.
- **`window.__grime`** (`render/world/Buildings.hx`) — the 3 grime materials, for live opacity tuning.
- **`window.__wild()`** (`render/wild/WildArea.hx`) — what the wilderness area on screen actually built: `{ ground, reliefAmp, rocks:[{col,row}], thicket:[{col,row}], batches:[{path,count}] }`. The two lists come back WHOLE, not as counts, because the question after "how many" is always "where is one" — an instanced batch carries no `userData.cls`, so `__dbg.find` cannot locate a prop out here and there is nothing else to aim a camera or a `go xy` at. `parasiteHx` reads `WildBand.cur` fine (statics) but never the `Wild` model, which needs an `AreaGame`. Attached on area build.
- **`window.__facility()`** (`render/facility/FacilityArea.hx`) — what the facility area on screen actually built: `{ structures:[{hangar,x1,y1,x2,y2,cells,reveal}], rooms, windows:[{col,row,len,alongX,inDir,structure}], doors:[{col,row,look,alongX,inDir,isOpen,live,t,yaw0,yaw1}], batches:[{path,count}], masts, ceilings, bulbs:[{col,row,y,mul}], lit }`. Same reasoning as `__wild` — an instanced batch has no `userData.cls` so `__dbg.find` cannot reach a park tree or a door leaf, and `parasiteHx` is statics-only so the `Facility` model is unreachable. Every question this kind raises is numeric and a screenshot cannot answer it: did the flood fill find three structures, is `hangar` the one it thinks, did every window run come back 2 or 3 cells, is the roof actually revealing (`reveal` is the live eased value per structure, 0 solid .. 1 open). A `doors` row carries the live state NEXT TO the geometry it drives — `isOpen` is what the model says, `t` where the eased swing has got to, `yaw0`/`yaw1` what the two leaves are actually holding (shut reads `0 / PI` or `-PI/2 / PI/2`, fully open both the same) — because a screenshot cannot tell a leaf hinged on the wrong jamb from one swinging the wrong way, and both just look like the door being inside the wall. `live` false means the cell found no `objects.Door` and can never open. The lighting rig answers the two questions it raises that a screenshot also cannot: did the lit-line rules put a `mast` on every kerb, lot edge and park path (and none inside a tree), and did every room get a `ceiling` fixture — `ceilings` should equal `rooms` unless a stale `generatorInfo` names a room the saved grid no longer has. `bulbs` is the candidate list the shared pool actually sees, masts (`mul` 1) and fixtures (`mul` `CEIL_MUL`) in one array; `lit` is how many of the 12 slots are claimed this frame. **`patches` is `{ tex, lawn, cells, strong, tufts }` — the park's overgrown-grass overlay (`render/facility/FacilityLawn.hx`), and `strong` is the only number it can be TUNED on**: `cells` is how many lawn cells were marked, but what the player sees is the coverage FIELD, and what shows through a near-uniform one is just the art's own ~41% opacity — grain over the whole park, which the wilderness pass misjudged by eye twice. `strong` is the share of the lawn's own bounding rect whose mask clears `alphaTest`, read live off the retained canvas; it is deliberately measured over the PARK and not over the 1024² canvas, which spans the whole 400-unit area rect and would report a fraction of a percent however overgrown the lawn was. Shipped at **20.3%** (6 seeds, 17 cells on a generated 12x25 park). Attached on area build.
- **`window.__progs()`** (`render/View.hx`) — live shader-program cache as `cacheKey` strings (`renderer.info.programs`). Diff the array before/after an action (e.g. first gas burst) to see which material permutations the driver compiles on first use — those first-use compiles are the frame hitches. Attached in `ensureCore`.
- **`window.host`** — Electron preload bridge (`save`, `settings`, `profile`, `mods`, `shell`, `debug`, …). `contextIsolation:true, sandbox:true` — no node APIs in the renderer.
- **In-engine debug keys** (street-debug mode, backtick): `1` lighting/bloom, `2`/`3`/`4` ambient/hemi/moon fill, `5` lamp spotlights, `0` all lights, `6` emissive, `7` shadow SAMPLING A/B, `8` reset perf peak, `9` draw-call breakdown dump (traced + copied to clipboard), `M` force every lit material matte. `7`/`8`/`9`/`M` + the perf HUD live in `render/StreetPerf.hx`; the console `perf street` toggle (`render.Actors.DEBUG_PERF`) shows the same HUD **without** locking game input, so it is the one to use while walking (debug mode owns the keyboard for the fly-cam).
- **Chasing a "why is this prop shiny/bright" art bug — `1` cannot answer it, `M` and `6` can.** `1` is WYSIWYG **albedo**: it hides every light and adds a full-bright ambient, so specular (which only exists under an analytic light) is gone by construction and whatever still looks wrong under `1` is the base-colour map. `M` clears metalness/roughness **and their maps** — the maps are what matter, since roughness/metalness are factors the map multiplies, so a mapped material stays glossy when only the factor is cleared. `6` isolates emissive. Baked glb props used to be the usual culprit — a PBR export lands at metallic 1 / roughness 1 with an MR map and read as chrome against the flat art — but a prop no longer HAS a specular path (`Models.toLambert`, see the models section), so `M` and `dropMR` are now no-ops on everything but the habitat props, and a prop that still looks wrong is its base-colour map: `baseColor` / `lift` in `models-src/models.json`, not shader work.
- **Measuring on a weak/integrated GPU** — the numbers lie unless you do all of this: **pin the camera** (`parasiteHx['render.Tools'].freeCam.lookFrom(...)` — `Tools.freeCam` is a static, so one pose reproduces exactly across reloads AND rebuilds; verify by `calls=`), **interleave A/B/A/B and take the MEDIAN** (means get destroyed by outliers — one run turned a real −19% win into a bogus −7% loss), **warm the shader permutations first** (keys `5`/`7` change the program key; the first toggle compiles a new set), and **never compare across sessions** — an integrated Radeon switches power state mid-run and the *identical* pinned frame was measured at both 11.61ms and 4.06ms. Shares (`1 − off/on`) survive clock drift; absolute ms do not. **The game window must be FOCUSED and in the foreground** — backgrounded, the compositor throttles to ~1fps and the timer query spans the whole idle gap, so `GPU` reads ~**1015ms** and an A/B comes out *inverted*. Any scripted sweep should filter samples (`GPU < 100`) and check the topbar fps before trusting a single number.
- **GPU-side (fill) A/B keys** — for when `GPU=` exceeds `submit=` and the frame is fragment-bound, which the draw-call keys above cannot see: `V` cycles the render scale (1.25 / 1.0 / 0.75 / 0.6, traced as `[render-scale]`; `View.setRenderScale` drives `renderer` + `composer` together), `Shift`+`1` toggles **bloom alone** (plain `1` flips lighting and bloom together), `Shift`+`5` toggles the **light cones alone** (plain `5` hides the 12 spotlights *and* the cones, so it cannot separate the per-fragment light loop from the additive cone overdraw). Return to baseline between measurements — `5` and `Shift`+`5` both touch the cone group.

## Console commands (`src/console/`)
- A new console command is **THREE edits, not one**. Miss any and it half-works:
  1. the handler + its routing branch (`src/console/<Group>.hx`, e.g. `Cult.hx`);
  2. its line in that group's **help block** (the `arr.length == 1` listing);
  3. its node in the **completion table** — `src/console/ConsoleCompletion.hx` (e.g. `cultSubs`, shared by the `cu`/`cult` aliases). Skip this and the command works but autocompletes nothing.
- Command aliases (`occasio`/`occ`) are routed in the handler, but only the **primary** name goes in the completion table.
- Args are declared in the completion table as `slot` nodes (`{ lit: 'br', next: [ { slot: '[amount]' } ] }`) — keep the slot names identical to the help line's.

- NEVER detach HEAD! NEVER!
- NEVER sweep stray .md files (review reports, notes, scratch docs) into commits unless directly asked; check `git status` for them before `git add -A`, or stage explicit paths.
- ALWAYS respond in English!
- ALWAYS run tests at the end of each task: cd src/ && make
- When changing persisted game data structures, ALWAYS verify Saver/Loader savegame compatibility (both serialization and load behavior, including old saves when relevant). Note that you should ask whether it is needed when planning (there might not have been a release yet)
- When modifying AI logic, see if additional ai traces are needed
- Use two-space indentation, brace-on-newline, and avoid trailing whitespace. in general, follow the existing code style of the file and repository.
- Lines without text should NEVER have whitespace.
- When adding new functions, always add short comment with summary of what it does on top, first letter should be lowercase
- When generating code, comment each large block with a short summary, first letter should be lowercase
- NEVER write var x = new Array<...>(), just write var x = []
- When writing if statements with multiple conditions, format each condition on a new line for better readability
- Multi-field object literals (options args, typedef instances, 3+ fields) are ALWAYS multi-line: `{` opens the block, each field on its own line, trailing comma, `});`/`};` closes. Never pack fields several-per-line.
- REFACTOR OVERLY LARGE ARG LISTS into a single options `typedef`. Past ~5 positional args — and ALWAYS when adding one to a signature already at that size — stop and convert instead of appending: a call site of bare `0`s and `true`s is unreadable and silently mis-orderable. Put the typedef in its own file named `<Thing>Opts.hx` next to its consumer, comment EVERY field on its own line, and say in the typedef's header comment which signature it replaced. Mark a field `@:optional` only when callers genuinely omit it (a lone call site wanting every value = keep them all required). See [`render/particles/PaintOpts.hx`](src/render/particles/PaintOpts.hx) (replaced 16 positional args) and [`render/particles/ProjectileOpts.hx`](src/render/particles/ProjectileOpts.hx) (replaced 10).
- NEVER pack multiple statements onto one line. No inline `{ a; b; }` blocks, no `if (x) { y; return; }`. Each statement on its own line, brace-on-newline (opening brace indented on the next line, body inside). A single-statement body may stay on its own line unbraced. This applies everywhere — guard clauses, loop bodies, self-check blocks, ternary arms.
- Method comments should ALWAYS start from the line start (no indentation)
- When creating variables or method names that have "id" in their name, use ID (e.g., memberID instead of memberId, getMemberID() instead of getMemberId()). Note: This applies to variable and method names only, not object properties like <object>.id which remain lowercase.
- When updating most of the code, keep changes compact: avoid introducing unnecessary temporary variables, redundant conditionals, or extra formatting helpers unless the existing code already requires them. Temporary variables are fine if they shorten the code or are reused.
- All enum values should be in ALL_CAPS_SNAKE_CASE (e.g., `enum ActionType { ATTACK, DEFEND, HEAL }`).
- stop unnecessary defensive checks. Prefer invariant-driven code for internal data structures and hot paths; only add extra null/bounds/type guards at real trust boundaries (user input, save/load migration, external APIs) or when existing local code already uses that guard pattern.
- for newly introduced internal data contracts (generatorInfo, mission hints, etc.), ALWAYS use explicit typed `typedef`/class fields. DO NOT use `Dynamic` unless the source is truly untyped external input.
- for metadata written and read by code introduced in the same change, DO NOT add migration/alias parsing helpers (`parse*` scaffolding, legacy key remaps) unless explicitly requested.
- keep fallback logic minimal and behavior-focused: allow `null`/missing optional fields, then fall back to existing gameplay behavior.
- compatibility shims are allowed only for real pre-existing persisted formats already in production saves; otherwise reject over-defensive parsing.
- any `Dynamic` usage in game logic MUST have an inline comment that states the trust boundary and why typed data is not possible.
- in `parasite-mod-sdk/externs/`, ALWAYS comment EVERY field and EVERY function of every typedef/extern (one-line summary above the line; first letter lowercase). Externs are the mod author's primary documentation surface — uncommented fields ship as silent API to third parties.
- Object/AI visual effects (flames, glows, auras, hit sparks tied to a world entity) must be FRONTAL-facing (fixed yaw, leaned back by `Sprites.TILT`, like the actor sprites) so they stay coplanar with and glued to their source from every camera angle — NOT camera-facing billboards. Camera-facing is only for free transient FX with no world anchor (loose embers/impact sparks). See `render.particles.Sparks` `flameQuad`/`glowQuad` (frontal) vs `streak` (camera-facing).
- Animation timing: every timed anim derives from [`render.RenderConfig.BASE_MS`](src/render/RenderConfig.hx) (base one-turn duration) as a plain multiplier (0.5×/1×/1.5×…), advanced each frame by `dtMs * ANIM_SPEED / BASE_MS` and scaled by the global `ANIM_SPEED`. NEVER hardcode milliseconds — a new anim's duration is `BASE_MS * <mult>`. (bullets etc. bypass and use raw dt.)

## 3D render changes: read the index + append the log
- [`docs/3d-render.md`](docs/3d-render.md) is the index: measurement rules, standing notes, open leads, and a verdict table with one row per experiment ever tried. **READ IT BEFORE proposing or starting any render change.** It is kept small on purpose — do not grow it beyond its table rows.
- [`docs/3d-changes.md`](docs/3d-changes.md) is the append-only log holding the full write-up of each entry. Find one by grepping the change text from the verdict table. **APPEND to it after trying anything** (including failures — those are the valuable entries), and add the matching row to `3d-render.md`; an entry with no row is invisible.
- **Entry shape: ~25 lines** — what changed, the measured numbers, the trap, the verdict. **Settled outcomes only**: no `IN PROGRESS`, no `pending`, no `TODO`, no "checked X and it was clean" narrative. If it is not settled, it is not an entry yet. When a new entry invalidates an old one, mark the old heading `> SUPERSEDED by <heading>`.
- `3d-changes.md` is capped: when it reaches ~2600 lines, `git mv` it to `3d-changes-<YYYY-MM>.md` and start a fresh one. The verdict table is what survives rolling, so the row matters more than the body.
- **Measure, never infer.** `calls=` in the `[street-render]` trace is the only draw-call number. The scene dump (`9`) is an INVENTORY: `visibleDrawables` counts objects with `visible` true, and frustum culling then discards most of them (measured: 1616 visibleDrawables → 435 calls). Never claim a draw-call win from the dump. A/B against a measured baseline in the SAME view (follow and tactical differ).
- `submit` is the CPU draw-call wall and the real ceiling — a better GPU does not fix it. `upd` (engine CPU) is ~1ms and almost never the problem.
- Batch only geometry that survives culling. `BatchedMesh` frustum-tests every instance on the CPU each frame, so batching mostly-culled objects is a PESSIMIZATION (an off-screen `InstancedMesh` is one bounding-sphere reject).

## Textures & image generation (3D city art)
- **"we need new images" / "new images" means GENERATE them with the gpt-image MCP tool** (not "the user will supply them"). Treat it as an instruction to run `generate_image`/`edit_image` yourself. Decals now come out of gpt already cut (see the transparent-background bullet); hand-cutting is only for what that route fumbles.
- **Default to 1k — do NOT ask.** Two MCP servers: `gpt-image-2` (1024 edge) and `gpt-image-2-2k` (up to 3840 edge). Use `gpt-image-2` unless the user explicitly asks for 2k. It is the right answer nearly always: outputs bake down to 512 (details/sprites 256), so a 1024 source is already oversampled. Reach for 2k only on the user's say-so.
- **One flat art style, from `style-flat.png`:** moody-night roguelike, matte flat colors, very dark/muted/desaturated palette, low contrast, even flat lighting, subtle fine grain, simple clean shapes, minimal detail. NO photorealism, NO realistic/volumetric lighting, NO glossy/specular reflections, NO camera/lens effects, NO soft photographic shadows — hand-painted, flat, like a 2D game tile. Append the canonical `style` string (top-level key in `textures-src/textures.json`) VERBATIM to EVERY gen/edit prompt; keep the two in sync.
- **Alpha comes from the API now: `background:"transparent"` (gpt-image-2 preview, on both MCP servers).** Send it with `output_format:"png"` (webp also carries alpha; **jpeg is rejected** — HTTP 400 `invalid_transparent_background_output_format`) and the drop has a real alpha channel. Measured on a test prop: 71.7% of pixels at alpha 0 and a 1–2px edge ramp — a cleaner cut than the `tol:24` chroma key. Two things ride along:
  - **Say NOTHING about a background in the prompt.** Describe one and the model paints one anyway. Still say the subject must not touch the frame edges.
  - Opaque pixels land at alpha **253, never 255**. Harmless here (`alphaTest` is 0.35–0.5 everywhere, `has_alpha` wants `lo < 255`) — just never write an `alpha == 255` test.

  Register the drop `class:"sprite"`, `needs_alpha:true`, NO chroma: `make tex` keeps the cut, and `bleed_alpha` scrubs the coloured glow gpt paints into the transparent texels. `edit_image` takes `background` too (verified re-cutting `decals/detail-ac.png`), so an opaque source can be re-emitted with alpha instead of hand-cut.
- **Fallback — the FLAT SOLID grey `#5a5d63` route**, for whatever transparent mode fumbles, and still MANDATORY for TRELLIS reference images (3D models section below). Generate on flat grey with the subject clear of the frame edges, register `class:"chroma"` (`chroma:"0x5a5d63"`, `tol:24`), and `make tex` bakes the key → alpha. On this route **NEVER ask the prompt for a "transparent background"** — with `background` unset gpt PAINTS A CHECKERBOARD as real pixels, a two-tone grid fused into the art that is strictly harder to cut than one flat colour.

  Windows/facades that must be transparent otherwise stay opaque and the tool warns until hand-edited.
- **Pipeline:** sources (1024²) in `textures-src/`; `textures-src/textures.json` is the source of truth (per label `{ src, class: tile|window|chroma|sprite, res?, needs_alpha, chroma?, tol?, prompt }`; `default_res` 512, details/sprites 256). Runtime outputs are build artifacts in `app/textures/<label>.png` (paths in `src/render/RenderConfig.hx` `TEXTURES`, loaded via `src/render/Textures.hx`) — never hand-place them. Subfolders are supported: a label/`src` like `decals/graffiti-1` nests both source and output (decals live under `textures-src/decals/` + `app/textures/decals/`). After generating/editing a source, update its `textures.json` entry (esp. `prompt`) and run **`make tex`** (→ `tools/textures.py`; also strips gpt prefixes and sweeps `*~` backups), then `make -C src` + reload.
- **Never manually `mv`/`cp` generated drops** (it trips a permission prompt). Generate straight into `textures-src/` (or a subdir) with `filename_prefix=<final-label>`, then run **`make adopt`** (`textures.py --rename`) — it strips the `image-<ts>-<hash>-` prefix in place (walks subdirs). Then `make tex`.
- **Batch gen in parallel:** issue independent `generate_image`/`edit_image` calls in ONE message (they're independent + slow). For lit/unlit pairs, make the unlit base first, then fan out lit edits.
- **NEVER stretch a texture** (any surface — walls, ground, roads, decals). World-aligned tiling on BOTH axes (`uv = worldPos/TILE` or `texture.repeat = faceLen/TILE`); accept a partial tile at a far edge. If stretching is ever unavoidable, STOP and notify the user. And NEVER put a flat solid-color material on visible geometry — always a texture.

## 3D models: image → glb → the game

- **A new prop is generated, not hand-modelled.** Four steps: `generate_image` (gpt-image-2) → **`image_to_3d`** (the `runware-trellis-2` MCP, Microsoft TRELLIS 2 on Runware) → an entry in `models-src/models.json` → **`make models`**. ~$0.03 and a couple of minutes per prop. The MCP server lives at `~/git/runware-trellis-2-mcp` (one tool, node/TS, `pnpm build`); `RUNWARE_API_KEY` comes from the shell env, and its default output dir already resolves to `<git root>/models-src`, so **do not `mv` the glb** — it lands where `make models` looks.
- **Every number the rules below are written in comes out of [`tools/propstat.py`](tools/propstat.py), and it takes either end of the pipeline.** `python3 tools/propstat.py <prop>.glb` reports tris, split ratio, connected components + largest share, bbox `widest/height`, albedo (whole-atlas AND sampled at tri UV centroids), texels-per-triangle with the `tex` that lands in band, and the MR verdict — each with a pass/REJECT read, and a starting `baseColor` or `lift` when the bake is out of the 46-52 family. `<ref>.png` reports subject value against the p50 69-77 that bakes correctly, frame margin, bbox aspect and the backdrop's real colour. `<ref>.png --lift 70 -o out.png` and `--fit 80 -o out.png` apply the two in-code reference corrections below. Run it on the source before wiring a prop in, and on the built glb after `make models`.
- **The reference sets the COMPOSITION; the settings set the TOPOLOGY. Do not blame one for the other.** ONE object, centred, whole, clear of the frame edges, on the same flat solid grey `#5a5d63` the texture pipeline falls back to (no ground plane, no cast shadow, no horizon), with the canonical `style` string appended verbatim. Keep the grey here — gpt's `background:"transparent"` is untested as a TRELLIS reference and TRELLIS wants a uniform backdrop to segment against. A cropped or cluttered reference comes back a blob. **And "three-quarter" is about the ATLAS, not only the silhouette — shoot it ISOMETRIC, from above one corner, so the TOP face and a SIDE face of every part are both in frame.** `facility/barrier` is the entry that proves it: a near-flat side elevation gave a perfectly good MESH (2 components at 86.2%, 1.22x split, correct proportions) and a **junk texture** — the arm's top and back faces are simply not in a side view, so TRELLIS invented them and the baked hazard stripes came back bleached and disagreeing chart to chart. Re-shot isometric at ~35° from one corner, with the stripes stated to wrap continuously over the edge from top face to side face, the same object baked a coherent atlas. A face the reference never shows is a face the generator hallucinates. **What the reference does NOT decide is how the surface fragments** — that headline used to read "the reference decides the mesh, far more than any setting" and a one-variable probe killed it: the *same* image that produced 96 disconnected blobs came back **1 component at 100%** on the corrected settings alone. The tidy story (every dark gap in the art becomes real air) fits the data and is still wrong. When a mesh comes back fragmented, re-run the settings before repainting anything.
- **Three reference fixes that are free, and one gpt defect they cover.** A reference can be corrected **in code** instead of re-prompting — a gamma on the subject (`--lift`), a shrink off the frame edge (`--fit`), and a re-lay on a truly flat backdrop, all of which hold the composition fixed so the next bake differs by *one variable*. That is how "is it the value or the shape?" gets answered for $0.01 instead of $0.24, and it is the answer to propstat's own **"TOUCHING THE EDGE, comes back a blob"** gate: gpt lays a long diagonal object corner to corner however loudly the prompt asks for a margin, and a re-roll gives a *different* composition where `--fit 80` gives the same one, smaller (`facility/barrier`: margin l 13 r 2 t 0 → 89/79/187, scale 0.947). They also fix a defect worth knowing about: **gpt paints a vignette**. Asked for flat `#5a5d63` (90/93/99) it delivered a backdrop measured at **82/86/91** with a gradient across it — darker than requested, which narrows the subject/backdrop margin TRELLIS segments on exactly when a dark subject needs it widest. **Key the correction against the backdrop gpt ACTUALLY PAINTED, not the nominal `#5a5d63`**: 42 apart in propstat's metric is past the soft key's foot, so nominal keying leaves the whole backdrop ~24% opaque — invisible when `lift` re-lays the WHOLE frame, and a hard rectangle border when `fit` pastes a sub-rect.
- **A BOX IS NOT A PROP — before generating anything, ask whether its silhouette is worth generating at all.** If the object is axis-aligned slabs (a kiosk, a bench, a cabinet, a low wall, a skip), EMIT IT: [`render/facility/FacilityGeom.hx`](src/render/facility/FacilityGeom.hx) has public `face` / `pane` / `cap` / `add` / `geom`, and [`FacilityTables`](src/render/facility/FacilityTables.hx) and [`FacilityEntry`](src/render/facility/FacilityEntry.hx) are both worked examples. What you get is exact proportions, the game's OWN tiling textures at full texel density (a prop's atlas is finite and spread over the whole model, so its density falls as the prop grows — see the texels-per-world-unit bullet below), and no unwrap lottery. Measured on the guard booth, generated first and rebuilt second: **7,431 tris → 34**, and the glb was a `propstat` REJECT anyway (40 components, largest 58.1%, 3.14× split, albedo 91/97/104) because a mesh generator handed a rectangular box returns a blob cloud of one. The same job also deleted a `models.json` entry, a `texSrc`, a generated emissive map and a warm row.
- **But "is it a box" is the wrong test, and it let the wrong thing through once. Ask instead: is this object carried by its SILHOUETTE or by its SURFACE?** The boom barrier beside that booth was exempted on the box rule — an arm, a counterweight and a cabinet genuinely IS more shape than a kiosk — and it was still wrong, because a boom barrier is not carried by its outline at all: **it is carried by its hazard bands**. The bake returned orange chevrons on tan where the reference painted red on off-white, and there is no fix on that path (`baseColor` is a per-channel MULTIPLY and can never put back contrast the generator merged away). Rebuilt as geometry with the bands as a tiling texture: **3,098 tris → 22**, and `propstat` had scored the glb almost exactly as it scored the booth (3 components, largest 65.9%, 2.07× split, albedo 145/125/105). A silhouette is what a mesh generator is for; a stripe, a rhythm, a material is what a tiling texture is for — it cannot lose contrast, cannot smear, holds density at any length and costs $0.01 to repaint. **Two smells that the surface is doing the work**: the `models.json` note is arguing for a hand-fitted `baseColor` off the family, or the object's whole read is a pattern you could name in one sentence.
- **Art for an emitted box wants to be UNIFORM along one axis, and that is worth prompting for explicitly.** `FacilityGeom.face`/`cap` take ONE period for both axes, so on a thin bar `v` is a narrow horizontal SLICE of the image at an arbitrary offset — a different one on the sides (`y/t`) than on the lid (`z/t`). Ask for vertical bands with no vertical structure and every slice is identical, so the pattern lines up across the lid and both sides for free and no second period is needed (contrast [`FacilityTables.panel`](src/render/facility/FacilityTables.hx), which needed one). Verify it: `max |row_mean − mean|` on the barrier drop is **0.010 on a mean of 0.311, 3.3%**. **Ask for "TILES SEAMLESSLY ON BOTH AXES", not for "uniform" — uniform is what you want, tiling is what makes it true, and gpt will hand you the difference.** Told only "completely uniform from top to bottom", it drew the cabinet's louvre slots with rounded ENDS a few pixels inside the top and bottom edges: a horizontal feature, therefore a seam, which landed as a plain band 10% up the box's faces and **somewhere else again on its lid**, since `cap` maps `v` to `z` where `face` maps it to `y`. A UV offset cannot fix that — it hides one seam and leaves the other, and both move with the object's world position. State that the pattern runs OFF the edges and is cut flat by them. Measured on the re-prompt: row deviation **0.00706 → 0.00150**, top and bottom rows within **0.0078** per pixel.
- **`lift` cannot do a level fit on TWO-TONE art — a material `color` can.** `lift` is a gamma, so it darkens the already-dark tone far harder than the light one: on the hazard bands (0.311 mean linear, 9.5× the asphalt) lift 1.6 took the red to **0.0276**, under the asphalt it stands over, and blew the red/white ratio from **6.8× to 13.8×** — white dashes floating with the red gone. A scalar on the material's own `color` is LINEAR, holds both the ratio and the hue, and moves only the level. Fit it live at the game camera; on two-tone art the DARK tone is what fails first.
- **ONE simple object per prop. If the idea is composite, SPLIT it and say so instead of generating it.** A prop that is several things at once — parts touching, rope through a handle, cloth draped over a box — comes back with a shattered atlas and cannot be decimated afterwards at any `error`. **Holes and lace are a SEPARATE case and no longer disqualifying**: on the corrected settings `wild/bush-bramble`, a tangle of interlocking canes with real see-through holes, came back a usable prop (16 components, largest **94.2%**, a correct radial silhouette) — but still split **2.59×**, the worst in this repo, so it can never be decimated offline and has to arrive at the budget. So holes cost you the offline route, not the prop; being several objects costs you the prop. Measured: the exit ladder (one hard object) unwraps at **1.18×** and meshopt takes 93,501 tris to 5,000; `sewer-pile-1` (rubble) **3.19×**; `sewer-pile-2` (two sacks + rope + a tarp + a broken crate) **6.8×** — it shipped undecimated at 19,712 tris with a 1024² map and *still* read as mush, because no tri budget buys back a silhouette the generator never resolved. So when the ask is composite, the answer is the split, not the job: "that is a crate + a sack + a cable coil — three props, scattered separately, one draw call each."
- **Prop ideas must be MODERN, and the word "modern" goes in the reference prompt verbatim.** The game is present-day. gpt-image defaults "sack" / "crate" / "barrel" to rustic-fantasy — that is how `sewer-pile-2` arrived as hessian, hemp rope and plank boards, which read wrong in a city sewer. Reach for present-day municipal/industrial objects (200 L steel drum, solid-walled plastic stacking crate, PVC-jacketed cable coil, tied refuse sacks, wheelie bin, traffic cone, junction cabinet, PVC pipe stack), and say **modern** in the prompt. Say **solid-walled** too where it applies: a lattice milk crate is all holes, which is the failure above.
- **Paint the reference MID-VALUE. A near-black subject comes back with a hallucinated albedo, and no seed fixes it.** TRELLIS decomposes the reference into albedo + lighting; where the subject is nearly black it reads the darkness as *shadow* and lifts the base colour, hue and all. `sewer/bags` (black refuse sacks, reference luma p05 30) baked at mean sRGB **77/62/99** — violet, from a cool 68/72/77 reference — while the drum, crates and cable of the same batch (p05 35-45) all came back correct. Regenerating on a fresh seed made it *worse* (mean 110/89/114, bimodal pink-on-black). **Repainting the reference is what actually fixed it**: the same subject at mid charcoal (subject p05 30 → 48) came back at 67/70/78, cool and neutral, tracking the reference's own hue. So aim a dark prop at mid charcoal (~`#3a3d42`) and let `baseColor` darken it in the bake — that direction works, the other does not. **`#3a3d42` is a FLOOR for the darkest pixels, not a target for the whole subject** — aiming the *whole* plant there put `wild/bush-bramble`'s reference at subject luma p50 53 and it baked at 24/23/21, half the prop family. The references that bake correctly sit at **subject p50 69-77** (conifer 69 → 54/58/50; the gappy bush 77 → 84/109/61). Measure the reference before spending on it. `baseColorFactor` is a LINEAR per-channel multiply: it can drop the level and even neutralise a cast, but it can never recover a channel the generator threw away — for the other direction there is now `lift` (below), a gamma on the map. Also: TRELLIS is **not bit-deterministic** — the same seed and inputs re-ran 4,769 tris as 4,627, so a seed reproduces the look, not the file.
- **The reference is archived beside the model as `<label>-src.png`**, automatically by `image_to_3d` — a mesh cannot be regenerated or re-judged without the image it came from, and the gpt output dir is scratch. The `-src` suffix is load-bearing: `models.mjs` treats a bare `<label>.png` as a `texSrc` base-colour OVERRIDE, so archiving the reference under that name would silently repaint the prop.
- **`remesh_project` and `mesh_cluster` are the two knobs that decide topology, and the API defaults for both are wrong.** `remesh_project` snaps the dual-contour remesh back onto the generated surface; the API defaults it to **0** (no snap-back at all, so the prop arrives rounded off). `mesh_cluster` reaches that same remesh — not just the UV atlas, which is what its name suggests and what got it dismissed once — so its `smoothStrength` and `thresholdConeHalfAngleRad` change surface CONNECTIVITY. `image_to_3d` now defaults both to the web playground's values (**0.9**, and `{globalIterations:1, refineIterations:0, smoothStrength:1, thresholdConeHalfAngleRad:PI/2}`), so just omit them. `remesh_project`'s wire range is `(0, 1]` — a literal `0` is rejected, omit instead. **These two are worth $0.01 to re-run before any repaint**: on one gappy reference they moved it from 96 components / 24.3% largest to **1 / 100%**. A prop that came back mushy or shattered and was blamed on the tri budget or the art was really this.
- **Count a prop's CONNECTED COMPONENTS before wiring it in — the split ratio cannot see "mostly empty".** Union-find over triangle edges keyed on **unique positions**: split ratio describes the ATLAS, components describe the SURFACE, and a prop can look fine by every number already measured while being a cloud of disconnected blobs. Measured: `rock-boulder` **1 / 100%**, `bush-low` **8 / 98.7%**, `tree-broadleaf-full` **17 / 93.9%**, a retired bush **96 / 24.3%** — that last one had the same bbox and unique-position count as its replacement, so nothing else would have flagged it. Read the gate as **few components, each holding a substantial share**, not as a raw count: the shipped conifer is 2 at 51/49 (canopy plus trunk) and `tree-broadleaf-full`'s 16 extras are specks sharing 6.1%. What fails is a *largest share* under ~90%.
- **Keep a high-target master in `models-src/`, and generate the game source separately.** `models-src/` holds sources and a pre-crushed one cannot be recovered, so archive `<label>-100k.glb` (same idiom as the existing `street-lamp-raw.glb` / `street-lamp-100k/`). But for a subject meshopt cannot decimate — see the split-ratio bullet — the file `models.json` points at has to arrive at the game budget already, so generate it with `decimation_target` set to that budget and `"tris": -1`. Runware unwraps and bakes *after* its own decimation, so its output is clean at any target.
- **The split ratio predicts the LANDING POINT, and ~2× is the line between the two workflows.** meshopt never hits the `tris` target on a TRELLIS export; the seam network floors it, and where that floor sits is what the ratio tells you. Measured on one batch of four, all asked for 1200: drum (1.31×) → **4,826**, crates (1.96×) → **23,926**, cable (2.10×) → **30,431**, bags (12.1×) → undecimatable. So judge against the prop budget, not the target: **below ~1.5× the 100k-master-plus-offline-decimate route works** and lands on a normal prop (4,826; the exit ladder ships at 5,000). **At ~2× and above it does not**, and that subject has to be regenerated with `decimation_target` at the budget.
- **Check how the subject unwraps before choosing the bake — vertex count over UNIQUE POSITION count.** meshopt cannot collapse an edge across an attribute discontinuity, so the split ratio predicts everything. The exit ladder: 55,080 verts over 46,778 positions = **1.18×**, large clean charts, and meshopt took it 93,501 → 5,000 exactly. The rubble piles: 130,974 over 41,042 = **3.19×** and 201,441 over 29,452 = **6.8×** — near-per-triangle charts, an attribute break on every edge. A hard-surfaced subject (ladder, pipe, crate) unwraps cleanly; a crumpled organic one (rubble, sacks, cloth) does not, because curvature everywhere means charts everywhere.
- **`error` does not unlock a shattered atlas — but on a CLEAN one it is worth a sweep.** On the 96k pile-1 source (3.19×): 0.005 → 54,718, 0.02 → 52,252, **0.30 → 52,184** — 60× the default cap for the same answer, and `meshCluster` at 16 global / 8 refine iterations moved 3.19× to 3.15×. Do not spend money re-generating to chase that. (That last number is about the ATLAS and does not contradict the connectivity result above: cranking the *iteration counts* barely moves the split ratio, while `smoothStrength` / `thresholdConeHalfAngleRad` at the playground values are what took a mesh from 96 components to 1. Different fields, different effect.) The trap is generalising it: swept on the low-ratio drum (1.31×) the same knob went 4,826 → 3,762 → 3,476 → **3,294** (asymptote by 0.1), a real **−32%**, while crates (1.96×) moved only −8% and cable (2.10×) −16%. So: sweep `error` before accepting a clean subject's tri count; do not bother on a shattered one.
- **`tex` is NOT a free knob, and getting it wrong looks exactly like a bad mesh. Always divide it by the tri count: TEXELS PER TRIANGLE.** A TRELLIS 2048 export is authored at ~43 (96,971 tris over 4.2M texels). The first pile shipped at 4,673 tris / `tex: 256` = **14**, and every crack line and grain speckle in the source was gone — read as smooth flat shards, which is what "looks like garbage" meant. `tex` was not shrinking the map, it was deleting it. Hold the ratio near the source's: 4,821 tris wants `tex: 512` (51), 19,223 tris wants `tex: 1024` (52).
- **But texels/tri is a FLOOR, not a target, and on a `tris: -1` prop it is blind to blur.** That ratio was fitted to the decimate-a-100k-master route, where the atlas and the tri count shrink together. A prop generated AT the budget has no such coupling: Runware bakes a **2048 atlas for a ~4.9k-tri mesh**, about **862 texels/tri at source**, so `tex: 512` throws away ~16x the texels while still reporting a healthy 53/tri. What catches it is **TEXELS PER WORLD UNIT** — the UV area in texels over the world triangle area, `sqrt` of the ratio, area-weighted over the mesh AT THE `h` THE GAME DRAWS IT. Measured: `tree-broadleaf-full` at `tex: 512` is **25/unit** over 292 u² of canopy, against ground/walkway/lawn tiling at 512/`GROUND_TILE` 9.0 = **57** and the grass tuft sprite at **171** — so the biggest prop in the park was the softest thing in the frame, reported as "blurry compared to grass/ground/walkway". `tex: 1024` puts it at **49**. The ground never has this problem because it TILES, so its density is constant however large the surface; a prop's atlas is finite and spread over the whole model, so density falls as the prop grows. **Check the big props, not the small ones** — `bush-low` at h 1.1 measures 108/unit and is already sharper than the ground.
- **Anisotropy was ruled out first and is NOT this — but glb textures were missing it.** `Textures.loadTexture` sets `anisotropy = 4` on everything the game loads by hand; `GLTFLoader` leaves every texture it makes at **1**, so props were the one thing in the frame unfiltered. Fixed via `RenderConfig.MODEL_ANISO` in `Models.get`. It is correct and free, but measure before believing it fixes a blur: in a frozen A/B (`ANIM_SPEED = 0`, HUD masked) forcing 1 → 4 moved **0.25%** of pixels by more than 2, where `tex` 512 → 1024 on the same pose moved **2.98%** — twelve times the effect.
- **Do NOT bake a TRELLIS atlas down to vertex colours.** Tried and reverted. The reasoning that killed it: the atlas looks like a mosaic of tiny patches, but the split ratio proves it is not per-triangle (130,974 verts is 1.36× the tri count; a true per-triangle atlas would be 3×), and each patch carries real sub-triangle detail — crack lines, grain, per-face colour. `COLOR_0` throws all of it away and the prop reads as smooth white shards. Two traps found on the way, worth knowing if it is ever right for a genuinely flat-shaded prop: sample the triangle's UV **centroid** (a vertex UV sits on a chart corner = the gutter, so it reads padding and bakes near-black), and `COLOR_0` is **LINEAR** while a baseColorTexture is sRGB.
- **`Models.instanced` keeps only the FIRST mesh of a glb** and drops the rest silently — `image_to_3d` returns `meshCount` so a multi-mesh drop is visible at generation time. TRELLIS normally emits one.
- **Never enable Draco.** `Models.get` builds a bare `GLTFLoader` with no `DRACOLoader`, so a Draco glb fails to load behind a `console.warn` and the prop is simply invisible.
- **A prop dense enough to OCCLUDE ITSELF bakes that occlusion into its albedo, and `baseColor` cannot undo it — that is what `lift` is for.** TRELLIS splits the reference into albedo + lighting, and a tangle, lace or dense canopy hands it self-shadowing it cannot tell from base colour. Measured: from the same reference value a conifer bakes at **0.79×** and `wild/bush-bramble` at **0.44×**, landing on 30/29/29 against the prop family's 46-52. Neither existing route reaches it — `baseColorFactor` is a factor in `[0,1]` and only multiplies DOWN, and repainting the reference tracks *proportionally* (the same image at subject p50 53 baked 24/23/21, lifted to p50 68 baked 30/29/29: 28% brighter reference, 29% brighter bake), so hitting 46-52 that way needs a reference brighter than the `#5a5d63` backdrop it must be segmented against. So the fix is `"lift"` in `models.json`: a gamma on the base-colour MAP, `out = (v/255)**lift`, `<1` brightens. Same name and meaning as `textures.json`'s. `lift` 0.78 put the bramble at **48/47/47**. Fit it by arithmetic off the measured bake, then re-measure the built glb — the whole-atlas mean and the tri-centroid-sampled mean should agree.
- **A prop does NOT draw with the material its glb ships.** `Models.toLambert` swaps every loaded glb material for a `MeshLambertMaterial` (map, normal, ao, emissive carried over) — the same flat material every ground, wall and roof in the game already uses, because the night art has no specular in it. **The exception is the switch: a glb whose `roughnessFactor` is under 1 keeps `MeshStandardMaterial`**, and `models.json`'s `roughness` dial is what bakes that — so `roughness` now means "this prop wants a specular highlight, keep it on the PBR path" (only the habitat props, 0.30-0.45). For every other prop the MR map is never sampled, which makes `dropMR` a no-op and takes a metallic-1 bake off the table as a bug class. **Why it is not just hygiene: it was the single biggest render win in the facility.** A TRELLIS prop is ~5k tris over a 40-pixel silhouette, so its triangles are SUB-PIXEL, the fragment shader runs once per 2x2 quad however small they get, and prop cost therefore tracks TRIANGLES and barely moves with resolution. Measured on the integrated Radeon, park in frame, 3.6M tris at 1080p: **31.4ms → 20.3ms GPU (32 → 49fps)**; culled follow view 8.99 → 6.58. Full numbers in `docs/3d-changes.md`.
- **A generated PBR export lands at metallic 1 / roughness 1 with an MR map.** That is not automatically wrong — the exit ladder's reads correctly as dark metal and had `dropMR`/`baseColor` reverted. `dropMR` + `baseColor` in `models.json` are the fix if it really does read as chrome, not shader work. **Both are now dead letters for any prop on the Lambert path (above); they still apply to a `roughness`-dialled one.**
- **Read the MR map itself before guessing — it is one image and it answers the question outright.** glTF packs **G = roughness, B = metalness**, so a dump of the baked texture is decisive: `sewer-pile-1` came out pure green (rough dielectric, correct) and `sewer-pile-2` came out **cyan** — metalness 1 across sacks, wood and cloth alike. That one needed `dropMR`; its neighbour, from the same generator on the same day, did not. **A uniformly metallic prop renders BLACK under debug key `1`**, not chrome: WYSIWYG hides every light, a metal has no diffuse term, and with no analytic light and no env map there is nothing left to shade. So key `1` showing a black prop is the metalness tell, and `M` confirms it.
- **A prop that has to GLOW takes an emissive map, and on a TRELLIS atlas that map is GENERATED, not hand-painted.** `emissiveSrc` in `models.json` (+ `emissiveStrength`, default 3, HDR so bloom catches it) is the street lamp's own route and it is the right one for any fixture — a quad hung at the bulb is fixed-yaw by construction and reads as a sticker on a prop that yaws. The atlas layout being unknown is not the obstacle it looks like, and there is a tool: **[`tools/emissive.py`](tools/emissive.py)** — `--bbox` prints the mesh frame, `--box x0,x1,y0,y1,z0,z1` selects triangles by CENTROID in that frame, and it rasterizes their UV triangles into a tinted mask (`models.mjs` pins `emissiveFactor` to `[1,1,1]`, so the hue lives in the map). **Run it on the BUILT glb, never the 100k master**, or the mask misses a chart the decimation moved. Five things it exists to enforce, each learned by shipping the mistake:
  - **Select by a BOX, not by normals.** A `NORMAL`-based "downward-facing faces" filter reads plausible and is unverifiable; a box is stated in printed coordinates and shows up in the preview.
  - **The dilation is the thing that puts glow where it does not belong.** The push into the chart gutter (needed so a resize and bilinear sampling do not read black at a chart edge) reaches the NEXT chart on a mosaic atlas, and that chart is an unrelated part of the surface. Measured on `facility/lamp-post`: **22 unselected triangles lit, from y −0.498 to +0.484 — the mast, down to the base plate.** The tool masks the dilation against every unselected triangle's coverage and **reports the bleed count; ship only at 0.**
  - **Rasterize CONSERVATIVELY, and check per TRIANGLE — a mask can measure clean and still speckle.** `PIL.ImageDraw.polygon` fills by pixel CENTRE, so a chart thinner than a texel covers *nothing at all*, and a TRELLIS atlas is full of those: invisible to the bleed mask, still sampled by the GPU. So supersample 4x and max-pool down (covered = ANY part of a triangle falls in the texel), add `outline=255` for a triangle even that misses, and grow the unselected coverage by 1 texel before subtracting, because bilinear reads a 2x2 neighbourhood. The CHECK needs the same care: testing each unselected triangle's UV *centroid* misses a triangle with one lit corner, which still draws a speck. Measured — a mask the centroid test called clean bled onto **9 triangles down the pole**.
  - **A flat mask is right for a LENS and wrong for a WINDOW RUN — that is what `--modulate` is for.** The flat mask lights every selected texel equally, which is correct for one small bright thing and is a *white card stuck on a black box* for a big region whose whole read is its structure: `facility/booth`'s glazing lit flat lost its mullions entirely, and dropping `emissiveStrength` from 2.2 to 1.1 only made the card dimmer — the halo went and the card stayed, because the failure is uniformity, not level. `--modulate` multiplies the mask by the glb's **own base-colour map**, which already separates the panes from the frames by ~3x in value, so the glow lands on the glass and the mullions stay dark for free. It costs brightness (that booth's lit texels went 255 → mean 117), so the strength goes UP to compensate — 3.5 there against a flat map's 2.2 — and only the panes then clear `BLOOM_THRESHOLD`, which is the "lit window" read rather than a lamp.
  - **Author at the entry's own `tex`** (320 for that prop), not 512: `models.mjs` resizes the emissive too, and the resize re-introduces the ramp the bleed mask just removed.
  - **`--preview` renders 3 orthographic views with the selection in red, framed ON THE SELECTION** — a lens is 2% of a 6-metre mast and is one pixel in a whole-prop view. Look at it before `make models`.
- **Where the glow goes is an ART call the camera decides, and it is not the physically-correct face.** A flat slab head lit whole reads as a glowing card, because its biggest face is the TOP and the camera looks down. The physically-right answer — the lens on the underside — is **invisible from an overhead camera**, and leaves the cone and the ground pool to carry the "it is on" read. A glow you actually want to SEE has to be on a face the camera can see, so widen the box deliberately rather than reaching for realism.
- **Warm every new glb path in `View.hx`'s `Models.get` promise chain**, and one entry per material variant it will ever draw (`SOLID`/`GHOST`/`HULL` each compile their own program). Instanced beside the rest of the warm scene it lands after `compileAsync` has walked it and compiles on first area entry instead.

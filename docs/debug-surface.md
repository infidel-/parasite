# Debug surface: what CDP can reach in the running game

How to drive and inspect the live Electron app, what instrumentation already exists, and the rules
for measuring anything on it. Loaded on demand — `CLAUDE.md` keeps only the one rule that has to
fire unprompted (ASK before adding a hook).

**New findings go here, not into `CLAUDE.md`.** One bullet per hook or lesson, the number that
proves it inline. When a lesson invalidates an old bullet, replace it rather than appending a second.

## Driving the running game (CDP / smoke-test)

- The Electron app runs with `--remote-debugging-port=9300`; the `chrome-devtools` MCP is wired to it (`172.18.208.1:9300`, WSL→Windows host). After `make reload`, drive/inspect the live app with `mcp__chrome-devtools__*` (`list_pages` → `evaluate_script` / `click` / `list_console_messages`) to smoke-test clicks and catch runtime exceptions.
- `list_pages` shows both the game (`file:.../app.html`) and, if open, DevTools — match `file:` + `app.html`. First MCP call may transient-fail; retry once.
- **FIRST call of every CDP session is `select_page` with `bringToFront: true`** — `list_pages` for the id, then `select_page({ pageId, bringToFront: true })`, which issues `Page.bringToFront`. `bringToFront` is optional and defaults to OFF, so it never happens unless asked for. Minimise the game or bury it under the terminal and Chromium stops compositing: `requestAnimationFrame` never fires and anything awaiting a frame never resolves, so `evaluate_script` and `take_screenshot` hang for the MCP's full 180s `protocolTimeout` (not configurable — there is no CLI flag) while `list_pages`, a browser-level call, still answers cheerfully. Browser-level call works + page-level call hangs = **hidden window**. One call up front removes the whole class of hang. Borrowed from `~/orwell/cdp/probe.mjs`, which does it before every eval.
- **`backgroundThrottling: false` is already set** (`electron/MainElectron.hx`, and present in the packaged build). It does NOT cover this: it relaxes timer throttling for a *visible-but-backgrounded* page, while a minimised or occluded window stops compositing outright. Do not reach for it again.
- **A raised CDP target is still not a focused OS window.** After `bringToFront` the HUD can still read **1 FPS** — enough to screenshot and evaluate, nowhere near enough to measure. Check the topbar fps before trusting any timing (see the measurement rules in `docs/3d-render.md`).

## Rules for the surface itself

- **ASK before extending the debug surface.** If a new/extended hook (`window.__*`, a debug key, a HUD readout, a trace) looks worth adding — say what it would expose and why, and ask. Do not add one unprompted: these are permanent instrumentation in shipped game code, they accrete, and the value is a judgement call the user makes. Using or reading the EXISTING hooks below needs no ask.
- **ALWAYS consider making a debug hook PERMANENT, not throwaway.** When a task needs a one-off hook to inspect live state, default to proposing it as a permanent, documented hook (added to this list) rather than a temporary one you rip out after — if it was useful once it is likely useful again, and re-adding it each time is wasted work. Ask (per the rule above), but frame it as permanent.

## What `evaluate_script` can reach

- **`window.parasiteHx` is the Haxe class registry (`$hxClasses`) — STATICS ONLY.** Do not burn turns BFS-ing `window`/`Main`/`GameScene` for the scene graph; it is not there. **The one instance a static DOES hand over is the whole game model: `parasiteHx['game.Game'].inst` is the live `Game`**, and from it `inst.area` reaches every `AreaObject` in the area — which is how a door was opened from CDP to check its swing without walking the player to it. Two gotchas: `area.getObjects()` returns a Haxe ITERATOR, not an array (`while (it.hasNext()) it.next()`, never `for...of`), and writing a field directly bypasses the object's own setter, so restore what you changed rather than leaving the save inconsistent. **The RENDER side hangs off that same instance and needs no hook: `game.scene.view3d` IS the live `render.View`** — `.scene` (the whole three graph, `traverse` it), `.camera`, `.renderer`, `.composer`, `.rig`, `.setRenderScale(s)`, and `.perf`, whose `lastGpuMs` is the real timer-query readout once `parasiteHx['render.Actors'].DEBUG_PERF = true`. That is a complete render A/B harness from CDP with nothing added to shipped code: walk the scene for the `InstancedMesh` batches, flip `visible`/`castShadow` or swap a material, and take the MEDIAN of `perf.lastGpuMs` over ~30 frames per phase (see the weak-GPU rules below). Two duties: **restore everything you touched** (materials, `visible`, `castShadow`, render scale, `DEBUG_PERF` — and any static you monkey-patched, e.g. a no-op `Models.cull` to freeze instance culling), and remember a reload wipes it all anyway. Anything the `View` does not own still wants a hook below (`untyped js.Browser.window.__x = {...}` from the class that owns the data). Pure functions ARE reachable: e.g. `parasiteHx['citygen.CityGen'].generate(seed)` regenerates any city headlessly, which is how you test city-layout claims across many seeds without loading a save. **Static STATE is reachable too, and that is the cheap way to verify a whole subsystem** — `parasiteHx['render.world.VisionMask']` hands over the live LOS mask's `canvas`, `wallLayer` and `opt`, so "is the shadow where the polygon says it is" is a `getImageData` and not a screenshot. It also runs the other way: calling `VisionMask.attach(SewerStyle.MASK, m.w, m.h, ...)` on a `SewerModel.demo()` regression-tests the tunnel branch without travelling to a tunnel. That CLOBBERS the live area's statics — reload afterwards.
- **`window.__check`** (`render/world/Check.hx`) — post-gen checklist: `pass`, `fails`, `windowless`, `doorless`, `noBackDoor`, `blank`, `counts`, `goto(i)`. Attached on world gen. Red badge in the topbar mirrors `fails`.
- **`window.__occ`** (`render/Occlusion.hx`) — building-fade bucketing: `stats()` → `{buildings, meshes, skipped}`; `skipped()` → `[{cls, size:[x,z]}]`, the meshes `pick()` left unbucketed, so they never fade. Expect ~9: the city-wide ground/kerb/markings, roof contact shadows, lamp posts and lamp cones all sit at `position (0,0,0)` (world-baked verts, or spread living in `instanceMatrix`) and are rejected by `pick()`'s size guard — without it they'd bucket into whatever building covers the grid centre and go see-through with it. A per-building mesh showing up here is a bug: it means it stopped fading. Attached on area build.
- **`window.__dbg`** (`render/Debug.hx`) — `count('door-cover-')`, `find('door-cover-stone')` → `[{cls,type,tris,pos,size}]`, `cam(cls, dist, up)` → frame the free-cam on the first match. **Gated: only exists after entering street-debug mode (backtick) once** — `attachTools()` builds it lazily.
- **`window.__grime`** (`render/world/Buildings.hx`) — the 3 grime materials, for live opacity tuning.
- **`window.__wild()`** (`render/wild/WildArea.hx`) — what the wilderness area on screen actually built: `{ ground, reliefAmp, rocks:[{col,row}], thicket:[{col,row}], batches:[{path,count}] }`. The two lists come back WHOLE, not as counts, because the question after "how many" is always "where is one" — an instanced batch carries no `userData.cls`, so `__dbg.find` cannot locate a prop out here and there is nothing else to aim a camera or a `go xy` at. `parasiteHx` reads `WildBand.cur` fine (statics) but never the `Wild` model, which needs an `AreaGame`. Attached on area build.
- **`window.__facility()`** (`render/facility/FacilityArea.hx`) — what the facility area on screen actually built: `{ structures:[{hangar,x1,y1,x2,y2,cells,reveal}], rooms, windows:[{col,row,len,alongX,inDir,structure}], doors:[{col,row,look,alongX,inDir,front,isOpen,live,t,yaw0,yaw1}], batches:[{path,count}], masts, ceilings, corridors, bulbs:[{col,row,y,mul}], lit, shadows, boards }`. Same reasoning as `__wild` — an instanced batch has no `userData.cls` so `__dbg.find` cannot reach a park tree or a door leaf, and `parasiteHx` is statics-only so the `Facility` model is unreachable. Every question this kind raises is numeric and a screenshot cannot answer it: did the flood fill find three structures, is `hangar` the one it thinks, did every window run come back 2 or 3 cells, is the roof actually revealing (`reveal` is the live eased value per structure, 0 solid .. 1 open). A `doors` row carries the live state NEXT TO the geometry it drives — `isOpen` is what the model says, `t` where the eased swing has got to, `yaw0`/`yaw1` what the two leaves are actually holding (shut reads `0 / PI` or `-PI/2 / PI/2`, fully open both the same) — because a screenshot cannot tell a leaf hinged on the wrong jamb from one swinging the wrong way, and both just look like the door being inside the wall. `live` false means the cell found no `objects.Door` and can never open. The lighting rig answers the questions it raises that a screenshot also cannot: did the lit-line rules put a `mast` on every kerb, lot edge and park path (and none inside a tree), did every room get its `ceiling` lattice, and did the `corridors` scan reach the passages no room rect can describe. **`ceilings` is NOT `rooms`** — a room takes `ceil(w / ROOM_SPACING) × ceil(h / ROOM_SPACING)` fittings, so on a generated compound 12 rooms come back as 30; what a stale `generatorInfo` shows up as now is a room whose lattice points all fail `isIndoor` and contribute nothing. **`corridors` is the one that is 0 only in a compound with no corridors at all** — they are in no list anywhere (`m.rooms` is `generatorInfo`'s room blocks), so they are scanned off the saved grid and a 0 here means the scan's predicate broke, not that the building is open-plan. `bulbs` is the candidate list the shared pool actually sees — masts (`mul` 1), room fixtures (`mul` `CEIL_MUL`), corridor fixtures (`mul` `CORR_MUL`) and door bulkheads in one array, so a bulb's family is readable off its `mul`; `lit` is how many of the 12 slots are claimed this frame, and it stays 12 however many candidates there are. **`shadows` is how many masonry rectangles `render.world.ContactMask` was painted from** (`render/facility/FacilityDetail.masonry`) — and it is the ONLY handle on that pass, because the contact shadow is a blurred FIELD sampled inside the floor materials and draws nothing at all: there is no mesh to find, no instance count to compare against, and it costs no draw call. `ContactMask.on` says whether an area attached one. **`boards` is how many lobby notice boards were emitted (`render/facility/FacilityBoard.hx`) and `front` on a `doors` row is what drives it** — one board per structure that has a front entrance, so `boards` short of the number of structures owning a `front` door means that entrance wall had nowhere to hang one. It is a MERGED mesh with no instance count, and `front` cannot be read off `look`: `FacilityModel.lookOf` collapses `FRAME_DOOR_DOUBLE` and `_GLASS` onto one painted pair, so a front entrance and a side door are the same `look`. On a generated compound: 4 `front` leaves (two entrances of two, flanking a mullion) and **2** boards. **`grime` is how many interior wall faces carry a damp band** (`render/facility/FacilityGrime.hx`) — one merged mesh, no instance count either, and since every eligible face takes one quad this IS the interior-face count. A 0 means the face predicate broke, not that the building is clean. Measured on a generated compound: **400 faces (97/101/101/101 by direction) off 252 solid lab wall cells**. It was briefly an instanced-quad pass and that version shipped visibly broken; if you are tempted back to quads, read its obituary in `ContactMask`'s header first. **`patches` is `{ tex, lawn, cells, strong, tufts }` — the park's overgrown-grass overlay (`render/facility/FacilityLawn.hx`), and `strong` is the only number it can be TUNED on**: `cells` is how many lawn cells were marked, but what the player sees is the coverage FIELD, and what shows through a near-uniform one is just the art's own ~41% opacity — grain over the whole park, which the wilderness pass misjudged by eye twice. `strong` is the share of the lawn's own bounding rect whose mask clears `alphaTest`, read live off the retained canvas; it is deliberately measured over the PARK and not over the 1024² canvas, which spans the whole 400-unit area rect and would report a fraction of a percent however overgrown the lawn was. Shipped at **20.3%** (6 seeds, 17 cells on a generated 12x25 park). **`roof` is `{ parapets:[{structure,skipped,cells,quads}], props:[{col,row,kind,structure}], hatches }`** — the roofline and what stands on it (`render/facility/FacilityRoof.hx`). `quads` is read straight off the buffers the emitter wrote, so it cannot drift from the geometry, and `skipped` reads off `hangar`: the hangar has no parapet and no props by construction, so a non-zero row there is the bug. A prop's `structure` is not decoration — it is what decides whether the prop draws at all, because a roof batch is culled with a MASK keyed on that structure's `reveal`, so one keyed to the wrong deck vanishes when the player walks into the building NEXT DOOR. **`roof.hangar` is `[{structure,span,rise,radius,arcDeg,seg,quads,gables,ridgeAlongX,ridge}]`** — the barrel vault, as the numbers it was DERIVED from rather than as geometry, because an arch is the one roof here a screenshot cannot check at all. Whether the section is really a circle segment is `radius` against `span` and `rise` (`radius == (span/2) / sin(arcDeg/2)`, and `arcDeg == 2·2·atan(2·rise/span)` in degrees); whether it is the shallow arc it is meant to be is `arcDeg` against the **180** a half-round barrel would read; whether the ridge took the long axis — which is what decides which pair of walls gets a gable crescent — is `ridgeAlongX`. `quads` is `seg` (the arch, in the fading deck) and `gables` is `2 × seg` (the two crescents, which are cladding and live in the structure's own wall mesh), both read off the emitter so neither can drift from the geometry. **`ridge` is there because `span` alone cannot catch a vault fitted to the wrong rect**, and that is not hypothetical: the vault used to take its box from `st.ox1..ox2`, the flood fill's bbox grown by a cell, and a door cell is ordinary lino floor so the fill ALREADY reaches into the wall ring at a doorway — the hangar's own side door took `ox1` one cell too far and the roof overhung that gable by 4 units with `span`, `radius` and `arcDeg` all still reading correctly. Attached on area build.
- **`window.__progs()`** (`render/View.hx`) — live shader-program cache as `cacheKey` strings (`renderer.info.programs`). Diff the array before/after an action (e.g. first gas burst) to see which material permutations the driver compiles on first use — those first-use compiles are the frame hitches. Attached in `ensureCore`.
- **`window.host`** — Electron preload bridge (`save`, `settings`, `profile`, `mods`, `shell`, `debug`, …). `contextIsolation:true, sandbox:true` — no node APIs in the renderer.

## In-engine debug keys

- **In-engine debug keys** (street-debug mode, backtick): `1` lighting/bloom, `2`/`3`/`4` ambient/hemi/moon fill, `5` lamp spotlights, `0` all lights, `6` emissive, `7` shadow SAMPLING A/B, `8` reset perf peak, `9` draw-call breakdown dump (traced + copied to clipboard), `M` force every lit material matte. `7`/`8`/`9`/`M` + the perf HUD live in `render/StreetPerf.hx`; the console `perf street` toggle (`render.Actors.DEBUG_PERF`) shows the same HUD **without** locking game input, so it is the one to use while walking (debug mode owns the keyboard for the fly-cam).
- **Chasing a "why is this prop shiny/bright" art bug — `1` cannot answer it, `M` and `6` can.** `1` is WYSIWYG **albedo**: it hides every light and adds a full-bright ambient, so specular (which only exists under an analytic light) is gone by construction and whatever still looks wrong under `1` is the base-colour map. `M` clears metalness/roughness **and their maps** — the maps are what matter, since roughness/metalness are factors the map multiplies, so a mapped material stays glossy when only the factor is cleared. `6` isolates emissive. Baked glb props used to be the usual culprit — a PBR export lands at metallic 1 / roughness 1 with an MR map and read as chrome against the flat art — but a prop no longer HAS a specular path (`Models.toLambert`, see the models section), so `M` and `dropMR` are now no-ops on everything but the habitat props, and a prop that still looks wrong is its base-colour map: `baseColor` / `lift` in `models-src/models.json`, not shader work.

## Measuring on the real hardware

- **Measuring on a weak/integrated GPU** — the numbers lie unless you do all of this: **pin the camera** (`parasiteHx['render.Tools'].freeCam.lookFrom(...)` — `Tools.freeCam` is a static, so one pose reproduces exactly across reloads AND rebuilds; verify by `calls=`), **interleave A/B/A/B and take the MEDIAN** (means get destroyed by outliers — one run turned a real −19% win into a bogus −7% loss), **warm the shader permutations first** (keys `5`/`7` change the program key; the first toggle compiles a new set), and **never compare across sessions** — an integrated Radeon switches power state mid-run and the *identical* pinned frame was measured at both 11.61ms and 4.06ms. Shares (`1 − off/on`) survive clock drift; absolute ms do not. **The game window must be FOCUSED and in the foreground** — backgrounded, the compositor throttles to ~1fps and the timer query spans the whole idle gap, so `GPU` reads ~**1015ms** and an A/B comes out *inverted*. Any scripted sweep should filter samples (`GPU < 100`) and check the topbar fps before trusting a single number.
- **GPU-side (fill) A/B keys** — for when `GPU=` exceeds `submit=` and the frame is fragment-bound, which the draw-call keys above cannot see: `V` cycles the render scale (1.25 / 1.0 / 0.75 / 0.6, traced as `[render-scale]`; `View.setRenderScale` drives `renderer` + `composer` together), `Shift`+`1` toggles **bloom alone** (plain `1` flips lighting and bloom together), `Shift`+`5` toggles the **light cones alone** (plain `5` hides the 12 spotlights *and* the cones, so it cannot separate the per-fragment light loop from the additive cone overdraw). Return to baseline between measurements — `5` and `Shift`+`5` both touch the cone group.

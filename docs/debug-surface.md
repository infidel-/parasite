# Debug surface: what CDP can reach in the running game

How to drive and inspect the live Electron app, what instrumentation already exists, and the rules
for measuring anything on it. Loaded on demand — `CLAUDE.md` keeps only the one rule that has to
fire unprompted (ASK before adding a hook).

**New findings go here, not into `CLAUDE.md`.** One bullet per hook or lesson, the number that
proves it inline. When a lesson invalidates an old bullet, replace it rather than appending a second.

## Driving the running game (CDP / smoke-test)

- The Electron app runs with `--remote-debugging-port=9300`; the `chrome-devtools` MCP is wired to it (`172.18.208.1:9300`, WSL→Windows host). After `make reload`, drive/inspect the live app with `mcp__chrome-devtools__*` (`list_pages` → `evaluate_script` / `click` / `list_console_messages`) to smoke-test clicks and catch runtime exceptions. **A WSL-side port scan is not a liveness test and never will be**: the app is a Windows process, so `ss -ltnp | grep 9300` in WSL comes back empty with the game plainly open on screen. Read once as "no game running", which killed a live A/B and shipped a report claiming a measurement could not be made. `list_pages` is the test.
- `list_pages` shows both the game (`file:.../app.html`) and, if open, DevTools — match `file:` + `app.html`. First MCP call may transient-fail; retry once.
- **Four local scripts drive the same port without the MCP, and they are faster for anything scripted**: `node probe.mjs "<expr>"` evaluates and prints; `node probe.mjs --wait "<expr>" [ms]` polls until truthy and prints the elapsed time (exit 2 on timeout, so it chains with `&&`); `make sshot` captures (`--wait` holds off while the fader is opaque — a capture during an area build is a black JPEG, not a stale one); `node keys.mjs <key|+delayMs>...` dispatches keys, matched on `e.code`, with `Backquote`, `Escape` and `Shift+N` for the debug keys below. All four share `tools/cdp.mjs`; override the host with `PARASITE_CDP=host:port`.
- **`make reload` lands on the MAIN MENU, so the hooks below read nothing — use `make reload-load`.** It reloads, waits out the ~4.6s boot warm, answers the "Autosave exists. Load?" offer `MainMenu` raises one tick after the menu, and returns only once the first frame has presented; `slot=N` loads a manual slot instead. The reload is what makes that autosave current — `Main`'s `beforeunload` flushes a forced autosave and `Page.reload` fires it. It prints the game's own `[street-warmup]` / `[mods]` console lines with a timeline, so the boot cost is measured on every reload rather than guessed at. It bails with the dialog text if the save's mod snapshot differs from the enabled set, since that prompt has resisted both a DOM click and a CDP key.
- **The boot phases are readable off statics — no hook needed.** `UIState` is an `enum abstract (String)`, so `parasiteHx['game.Game'].inst.ui.state` compares against a plain `'UISTATE_MAINMENU'` / `'UISTATE_DEFAULT'`. Warm-done is `UISTATE_MAINMENU` (`Main.reveal` is its only setter, and it fires on success, failure and the 30s backstop alike); loaded-and-painted is `isStarted` with `#fader`'s inline opacity back to `'0'`, which only happens from `View`'s `firstFrame` callback or its 5s backstop. `Game.inst.load(n)` is public — slot 0 is the autosave, 1..8 manual.
- **FIRST call of every CDP session is `select_page` with `bringToFront: true`** — `list_pages` for the id, then `select_page({ pageId, bringToFront: true })`, which issues `Page.bringToFront`. `bringToFront` is optional and defaults to OFF, so it never happens unless asked for. Minimise the game or bury it under the terminal and Chromium stops compositing: `requestAnimationFrame` never fires and anything awaiting a frame never resolves, so `evaluate_script` and `take_screenshot` hang for the MCP's full 180s `protocolTimeout` (not configurable — there is no CLI flag) while `list_pages`, a browser-level call, still answers cheerfully. Browser-level call works + page-level call hangs = **hidden window**. One call up front removes the whole class of hang. Borrowed from `~/orwell/cdp/probe.mjs`, which does it before every eval.
- **`backgroundThrottling: false` is already set** (`electron/MainElectron.hx`, and present in the packaged build). It does NOT cover this: it relaxes timer throttling for a *visible-but-backgrounded* page, while a minimised or occluded window stops compositing outright. Do not reach for it again.
- **A raised CDP target is still not a focused OS window.** After `bringToFront` the HUD can still read **1 FPS** — enough to screenshot and evaluate, nowhere near enough to measure. Check the topbar fps before trusting any timing (see the measurement rules in `docs/3d-render.md`).

## Rules for the surface itself

- **ASK before extending the debug surface.** If a new/extended hook (`window.__*`, a debug key, a HUD readout, a trace) looks worth adding — say what it would expose and why, and ask. Do not add one unprompted: these are permanent instrumentation in shipped game code, they accrete, and the value is a judgement call the user makes. Using or reading the EXISTING hooks below needs no ask.
- **ALWAYS consider making a debug hook PERMANENT, not throwaway.** When a task needs a one-off hook to inspect live state, default to proposing it as a permanent, documented hook (added to this list) rather than a temporary one you rip out after — if it was useful once it is likely useful again, and re-adding it each time is wasted work. Ask (per the rule above), but frame it as permanent.

## What `evaluate_script` can reach

- **`window.parasiteHx` is the Haxe class registry (`$hxClasses`) — STATICS ONLY.** Do not burn turns BFS-ing `window`/`Main`/`GameScene` for the scene graph; it is not there. **The one instance a static DOES hand over is the whole game model: `parasiteHx['game.Game'].inst` is the live `Game`**, and from it `inst.area` reaches every `AreaObject` in the area — which is how a door was opened from CDP to check its swing without walking the player to it. Two gotchas: `area.getObjects()` returns a Haxe ITERATOR, not an array (`while (it.hasNext()) it.next()`, never `for...of`), and writing a field directly bypasses the object's own setter, so restore what you changed rather than leaving the save inconsistent. **The RENDER side hangs off that same instance and needs no hook: `game.scene.view3d` IS the live `render.View`** — `.scene` (the whole three graph, `traverse` it), `.camera`, `.renderer`, `.composer`, `.rig`, `.setRenderScale(s)`, and `.perf`, whose `lastGpuMs` is the real timer-query readout once `parasiteHx['render.Actors'].DEBUG_PERF = true`. That is a complete render A/B harness from CDP with nothing added to shipped code: walk the scene for the `InstancedMesh` batches, flip `visible`/`castShadow` or swap a material, and take the MEDIAN of `perf.lastGpuMs` over ~30 frames per phase (see the weak-GPU rules below). Two duties: **restore everything you touched** (materials, `visible`, `castShadow`, render scale, `DEBUG_PERF` — and any static you monkey-patched, e.g. a no-op `Models.cull` to freeze instance culling), and remember a reload wipes it all anyway. Anything the `View` does not own still wants a hook below (`untyped js.Browser.window.__x = {...}` from the class that owns the data). Pure functions ARE reachable: e.g. `parasiteHx['citygen.CityGen'].generate(seed)` regenerates any city headlessly, which is how you test city-layout claims across many seeds without loading a save. **Static STATE is reachable too, and that is the cheap way to verify a whole subsystem** — `parasiteHx['render.world.VisionMask']` hands over the live LOS mask's `canvas`, `wallLayer` and `opt`, so "is the shadow where the polygon says it is" is a `getImageData` and not a screenshot. It also runs the other way: calling `VisionMask.attach(SewerStyle.MASK, m.w, m.h, ...)` on a `SewerModel.demo()` regression-tests the tunnel branch without travelling to a tunnel. That CLOBBERS the live area's statics — reload afterwards.
- **HOT-SWAPPING A TEXTURE TO A DIFFERENT SIZE FROM CDP RENDERS GARBAGE.** Reassigning `material.map.image` to a new `Image` and setting `needsUpdate` is the obvious way to see a re-run of `make tex` without a reload, and it works — *until the output resolution changes*. three allocates immutable mipmapped storage for a texture once, so the new image is uploaded into the old allocation and the mesh samples whatever that holds: measured on `facility/sink` going 512 → 256, the basin tore into fragments with pieces of the neighbouring atlas cell drawn under it, while the geometry read back exact, the built PNG opened clean and the uv rects isolated correctly. Build a **new `Texture` for the new image and `dispose()` the old one** instead. The general rule: when a live-patched scene disagrees with the geometry AND the source art AND the uv arithmetic, suspect the patch before the pass.
- **`window.__check`** (`render/world/Check.hx`) — post-gen checklist: `pass`, `fails`, `windowless`, `doorless`, `noBackDoor`, `blank`, `counts`, `goto(i)`. Attached on world gen. Red badge in the topbar mirrors `fails`.
- **`window.__occ`** (`render/Occlusion.hx`) — building-fade bucketing: `stats()` → `{buildings, meshes, skipped}`; `skipped()` → `[{cls, size:[x,z]}]`, the meshes `pick()` left unbucketed, so they never fade. Expect ~9: the city-wide ground/kerb/markings, roof contact shadows, lamp posts and lamp cones all sit at `position (0,0,0)` (world-baked verts, or spread living in `instanceMatrix`) and are rejected by `pick()`'s size guard — without it they'd bucket into whatever building covers the grid centre and go see-through with it. A per-building mesh showing up here is a bug: it means it stopped fading. Attached on area build.
- **`window.__dbg`** (`render/Debug.hx`) — `count('door-cover-')`, `find('door-cover-stone')` → `[{cls,type,tris,pos,size}]`, `cam(cls, dist, up)` → frame the free-cam on the first match. **Gated: only exists after entering street-debug mode (backtick) once** — `attachTools()` builds it lazily.
- **`window.__grime`** (`render/world/Buildings.hx`) — the 3 grime materials, for live opacity tuning.
- **`window.__wild()`** (`render/wild/WildArea.hx`) — what the wilderness area on screen actually built: `{ ground, reliefAmp, rocks:[{col,row}], thicket:[{col,row}], batches:[{path,count}] }`. The two lists come back WHOLE, not as counts, because the question after "how many" is always "where is one" — an instanced batch carries no `userData.cls`, so `__dbg.find` cannot locate a prop out here and there is nothing else to aim a camera or a `go xy` at. `parasiteHx` reads `WildBand.cur` fine (statics) but never the `Wild` model, which needs an `AreaGame`. Attached on area build.
- **`window.__facility()`** (`render/facility/FacilityArea.hx`) — what the facility area on screen actually built: `{ structures:[{hangar,x1,y1,x2,y2,cells,reveal}], rooms, windows:[{col,row,len,alongX,inDir,structure}], doors:[{col,row,look,alongX,inDir,front,isOpen,live,t,yaw0,yaw1}], batches:[{path,count}], masts, ceilings, corridors, bulbs:[{col,row,y,mul}], lit, shadows, marks, zones, points, placards, sinks, boards, grime, cabinets, exits }`. Same reasoning as `__wild` — an instanced batch has no `userData.cls` so `__dbg.find` cannot reach a park tree or a door leaf, and `parasiteHx` is statics-only so the `Facility` model is unreachable. Every question this kind raises is numeric and a screenshot cannot answer it: did the flood fill find three structures, is `hangar` the one it thinks, did every window run come back 2 or 3 cells, is the roof actually revealing (`reveal` is the live eased value per structure, 0 solid .. 1 open). A `doors` row carries the live state NEXT TO the geometry it drives — `isOpen` is what the model says, `t` where the eased swing has got to, `yaw0`/`yaw1` what the two leaves are actually holding (shut reads `0 / PI` or `-PI/2 / PI/2`, fully open both the same) — because a screenshot cannot tell a leaf hinged on the wrong jamb from one swinging the wrong way, and both just look like the door being inside the wall. `live` false means the cell found no `objects.Door` and can never open. The lighting rig answers the questions it raises that a screenshot also cannot: did the lit-line rules put a `mast` on every kerb, lot edge and park path (and none inside a tree), did every room get its `ceiling` lattice, and did the `corridors` scan reach the passages no room rect can describe. **`ceilings` is NOT `rooms`** — a room takes `ceil(w / ROOM_SPACING) × ceil(h / ROOM_SPACING)` fittings, so on a generated compound 12 rooms come back as 30; what a stale `generatorInfo` shows up as now is a room whose lattice points all fail `isIndoor` and contribute nothing. **`corridors` is the one that is 0 only in a compound with no corridors at all** — they are in no list anywhere (`m.rooms` is `generatorInfo`'s room blocks), so they are scanned off the saved grid and a 0 here means the scan's predicate broke, not that the building is open-plan. `bulbs` is the candidate list the shared pool actually sees — masts (`mul` 1), room fixtures (`mul` `CEIL_MUL`), corridor fixtures (`mul` `CORR_MUL`) and door bulkheads in one array, so a bulb's family is readable off its `mul`; `lit` is how many of the 12 slots are claimed this frame, and it stays 12 however many candidates there are. **`shadows` is how many masonry rectangles `render.world.ContactMask` was painted from** (`render/facility/FacilityDetail.masonry`) — and it is the ONLY handle on that pass, because the contact shadow is a blurred FIELD sampled inside the floor materials and draws nothing at all: there is no mesh to find, no instance count to compare against, and it costs no draw call. `ContactMask.on` says whether an area attached one. **`marks` is how many segments are struck on the INDOOR floors** (`render/facility/FacilityPaint.indoor`) — the aisle marking, which is a PAIR of lines bounding a walkway and never a centre line, so one segment is one cell of one line of one pair. A marked room contributes about twice its long axis, and a corridor cell contributes one segment per lane boundary it TOUCHES — so each cell of a two-wide corridor emits one, the middle cell of a three-wide emits none, and a cell at a junction mouth emits only the edge whose wall is still there. It is a static on `FacilityPaint` in `ContactMask.count`'s shape and for the same reason: the aisle is one merged mesh with no instance count. It is its OWN mesh and not the lot's, and the split is the colour and nothing else — an aisle is yellow (`MARK_COLOR`) and a parking bay is white, off one shared `city/ground-road-paint` map with two `color` uniforms, so it costs **+1 call and +0 programs** (`color` is a Lambert uniform, not a program key). Gated on `freeFloor`: `Surf.TILE`/`GRATE`/`LINO`, no `m.drain`, not a wall, not a doorway, no bench, no fitting. **`GRATE` is IN and `m.drain` is the test**, which is the model's own rule (*the surface says where a drain COULD be and the object says where one is*) and the first build broke it — the generator lays a grate tile in every chem lab and stands a drain on it only about a third of the time, `FacilityGeom.floorBuf` routes a bare grate cell to the ROOM floor buffer so it draws as ordinary tile, and skipping it left a hole in the line with nothing visible in it. Rooms and corridors are two passes because they are two shapes: a room is a rect in `m.rooms` with a long axis, a corridor is in no list anywhere and is read per cell off the two runs through it (`FacilityLamps`' own reading). **Most rooms correctly take none, because MARKING IS FOR TRAFFIC**: a lane narrower than `MARK_LANE_MIN` is the work aisle between two bench runs and takes no paint (a 3-cell room benched down both long walls leaves 1.6 units, which reads as one thick line), and a room whose derived pair is wider than `MARK_ROOM_MAX` has its two edges pulled in equally rather than left outlining the room (measured 25.6 units apart in a 9x10 lab). On a generated compound **9 rooms of 12** are marked, and the three misses are exactly the two 10x3 work aisles and the hangar (`Surf.CONCRETE`, which correctly takes none). A **0** everywhere means the gate broke. **The lane width is the minimum clear reach over the middle run with the REACH-0 CELLS DROPPED**, and that exclusion is not a refinement — the generator cuts a one-cell walkway through each bench run, so without it the free cell in that gap reports reach 0, sets the whole room's lane to 1.6 and drops the room (measured, 4 rooms of 12, and INVERTED: a room whose bench run BLOCKS its centre line is skipped by `freeFloor` and keeps its real 25.6, while one with a doorway through the run loses everything). Two consequences to read the number against: the offsets are now wide enough for a line to sit whole CELLS from the run it was derived from, so the paintable test asks the LINE's own cell as well as the run's (`strikes`) — the direct check is to bin every aisle quad to its centre cell and ask for that cell's tile, which must come back **0 buried** — and both lines have to PAINT at least HALF the run before either is struck, which is what still refuses the work aisles. That guard is a FRACTION and not a cell count on purpose: real lanes paint 50-100% (5/10, 6/10, 6/8, 7/8, 8/8, 4/5) and the work aisles paint 30% and 40%, and it is measured with the DOOR break excluded, since a lane is allowed to break and counting that gap rejected all 12 rooms. **Each corridor edge is emitted by the cell that TOUCHES it** (`reach().cells == 0` on that side), which is how the pass tells a passage from a BRANCH with no run list and why an edge can never land far from the cell that struck it; the earlier whole-cross-section test rejected both lines at a T though the branch opens off only one, breaking the through lane on its far side too. Three figures tie the markings into one network and each is worth reading off the mesh: a lane ends AT a doorway (no inset), a door opening onto a lane's SIDE breaks its line for that cell, and a lane running into a junction carries `MARK_WALL_CLEAR` past its own cell so it meets the through lane's line exactly — a branch line ending at row 11.58 against a spine line at row 11.58 is the mouth mitred correctly, and ending at 12.00 is the 1.7-unit gap that figure fixes. A quick correctness read: **no corridor cell should carry both an X-running and a Z-running quad** — bin each quad by its centre cell and any cell with both is an axis flip. Measured on a generated compound: **270 segments**, one quad each, +540 tris in a walked pose. **Two defects were found by eye after that number first settled at 275 and both were geometry the counters could not see.** (1) `MARK_ROOM_MAX` moves both lines AFTER `MARK_WALL_CLEAR`/`MARK_FURN_CLEAR` are applied and re-checks nothing, so a line can land back under a bench worktop — the top overhangs its cell by `BENCH_LIP` 0.2 at `BENCH_H` 2.0 and the line is `LINE_W` 0.18 wide, so anything closer than 0.29 to a boundary a bench is across is partly hidden. On a 6x8 lab the cap's arithmetic put both lines EXACTLY on a cell boundary and two quads were **100% hidden**. `MARK_LIP_CLEAR` pulls each line back inside its own cell; **the cell tests cannot see this and are not where to fix it** — `strikes` bins the line to `int(mid + 0.5 + s * off / CELL)` and `buried` bins the quad's CENTRE, and on a boundary both round to the free side while half the paint lies in the bench's. (2) `strikes` asked `mid`, the ROOM's middle cell, and the two offsets are derived independently and are NOT symmetric, so the middle can BE one line's own cell: on a 7x10 lab an island bench standing on `mid` removed three cells of the OTHER line, whose own column and the whole walkway between the pair were clear floor. It asks the cell one step INSIDE the line now — the lane it bounds — which also correctly drops the segments that were bounding a bench rather than a lane, and those were exactly the ones sitting in the one-cell walkway gap the generator cuts through a bench run. (3) **The overhang has TWO AXES and (1) only answered one**: a bench in the next cell ALONG the run lips 0.2 back over the segment's END, so a segment ending flush on the cell boundary still ran its last 0.29 under the top. The same `MARK_LIP_CLEAR` insets the end, and there it IS per cell — `strikes` asked of the neighbour along the run, whose two tested cells are exactly the two that can lip over this line; a neighbour dropped by the DOOR break still strikes, so the door gap keeps its measured width. **The whole-compound figure to hold is 0 of 270 aisle quads touching a bench-top quad**, measured as covered AREA and not covered WIDTH. **`zones` is how many KEEP-CLEAR hatches were struck** (`FacilityPaint.keepClear`) — one per exterior door leaf with circulation behind it, and the number to read it against is the TERMINAL half of `exits`, both being `FacilityExit`'s same terminal-door list: **6** on a generated compound, against `exits` 16 = 6 terminal + 10 directional. The two disagreeing means one of them has grown a placement rule of its own. A zone belongs to fire equipment, an electrical panel or an EXIT and never to a doorway as such, which is why there are 6 and not one per `doors` row; `freeFloor` is the "circulation behind it" test with nothing added to it, so the hangar's shutter drops out on its own (concrete inside, tarmac outside) exactly as it does for the signage. It is a merged mesh with no instance count, same blindness as `marks` beside it, and it is a THIRD mesh rather than a third tint on the aisle's: **it is a CUTOUT, red stripes with the real floor showing between them**, where every texel of the aisle's paint map is paint. It shipped OPAQUE for one build, with the gap painted as floor, and the reason that failed is worth carrying — an opaque hatch has to paint a floor it cannot match. Value it can: the drop's gap measured 0.1575 linear against the corridor lino's **0.1353** (and note the 0.0749 that sits in `floor-tile`'s own `note` in `textures.json` is stale text from before the lino was re-rolled blue-cyan; `built_linear` is the only current value). HUE it cannot — a neutral grey band on a pale blue-cyan floor reads as another material — and one bake cannot serve two floors, zones sitting on lino 0.1353 where a later storage hatch sits on room tile 0.1185. So the source is hand-cut, `needs_alpha: true` is the gate that refuses an opaque one by name, and `ZONE_CUT` 0.5 is the threshold; opaque + `alphaTest`, never `transparent`. Measured **+1 call, +12 tris, and progs 90 → 91** — `alphaTest` IS a program key and the guess that `FacilityDeco`'s own cut would cover it was wrong. It is WARMED, not compiled on first entry (facility warm 83 → 84 cached), so there is no hitch, and a second hatch is +0 against it. **`marks` and `zones` are COUPLED and it is the first claimed-cell list in the family** — markings never cross, and `MARK_WALL_CLEAR` cannot separate these two the way it separated the aisle from the casework, a zone lying in the open floor a lane runs down. The zone pass writes a `Bool` grid the aisle skips on, read at EMISSION and never inside `reach` (which walks clear floor to derive where a lane GOES, so a zone cell answering "not floor" there would move a whole section's lines), and zones are therefore built BEFORE the aisle in `FacilityPaint.build`. So `marks` drops by one per zone cell — 246 without them, 240 with. The direct check is the same XZ pair intersection the bend fix used, aisle quads against zone quads: **0 crossings**, 240 against 6. **`zones` has TWO sources and is only readable as their sum**: the door hatches above, plus one in front of every wall FITTING — so on a generated compound it reads **17 = 6 + 11**, and a `zones` under `points` means a fitting landed on a cell a door zone had already claimed. **`points` is how many corridor wall fittings stand** (`render/facility/FacilityPoint.hx`) — the fire points and the electrical panels, i.e. the things a keep-clear zone actually belongs to, since a zone with nothing over it is a stain. Merged mesh with no instance count, the same blindness as `exits`, and it is read against two rules: exactly **ONE PANEL PER STRUCTURE** that has a free corridor wall (so `points` minus the structure count is the fire points), and no two fittings inside `POINT_SPACING` cells of each other, measured between CELLS and not along one wall so a two-wide corridor cannot take one on each hand. A fitting also never stands on the LAST CELL of a wall run — the wall line must `FacilityGeom.carries` past it both ways, `FacilityKit.wall`'s own guard — because `FacilityGeom.slab` insets that face by a unit and a fixed-width quad centred on the cell then lands flush against the inset end, i.e. on the corner. Note the slab clamp does NOT catch it and cannot be used to check for it: the quad fits the inset face exactly, so it measures at full `POINT_W` either way. Measured on a generated compound: **11 = 2 panels + 9 fire points**, the 2 being the two lab buildings — the hangar is `Surf.CONCRETE`, has no corridor and correctly takes nothing. Both fittings are wall QUADS and neither is a prop: the silhouette-vs-surface guard answers a panel outright (a flat door with a label, no silhouette at all) and a fire point reads from this camera as its red backboard rather than its cylinder, so they are two cells of ONE atlas (`facility/wall-points`, `POINT_U_FIRE` 0.0 / `POINT_U_PANEL` 0.5) on one mesh and the family costs **+1 call, +22 tris and +0 programs**. The +0 there is worth how it was measured: `renderer.info.programs.length` is a session-cumulative cache and read across two poses this looked like +1, so the check that settles it is `renderer.properties.get(mat).currentProgram` on the fitting mesh and on the benches — **both program 64**, the interior-wall permutation. **`points` cannot exceed the free corridor wall faces left after `FacilityTables.runs` takes the casework's**, which is the one real collision in the family and the first in the compound that needed a check against another builder rather than a clearance: a cabinet and a fitting want the same wall face, and `MARK_WALL_CLEAR` works for the aisle only because a lane runs down the MIDDLE of a corridor. `runs(m)` is public and recomputed rather than recorded, a pure function of the saved grid, so neither builder has to run before the other; a `points` that jumps when `CASE_PCT` moves means that exclusion broke. The litter bins need no test of their own — `FacilityTables.hugs` rejects the dead-end and inside-corner cells, which are exactly the bins'. **`placards` is how many ROOM wall safety signs stand** (`render/facility/FacilityPlacard.hx`) — merged mesh, no instance count, the same blindness once more, and it is the only counter here that reads a SURFACE rather than a family: every other wall fitting in the compound is `Surf.LINO`-gated (`exits`, `points`, `cabinets`) or one per front entrance (`boards`), so a room wall carried the damp band and nothing else, at a measured **10.25% of the frame**. **One per RUN, and the sign NAMES WHAT STANDS UNDER IT** — a run being a stretch of `Surf.TILE` floor hugging unbroken `isSolidWall` masonry, ended by a DOORWAY (a door cell is not `isSolidWall`), so a wall with an opening in it is two runs and contributes 2, which is where a real pair is. `PLACARD_RUN_MIN` 3 drops the stubs. The pass walks the run and scores every cell by (which sign it earns, then whether the thing stands ON that cell or one step further INTO the room, then how far the cell is off the run's middle), so the plate lands over the bench, drum or rack it is talking about; the middle cell is only the FALLBACK for a run with nothing on it at all, and that is **0 runs** on a generated compound. **Both probes are scored and the second is not a fallback for the first** — asking behind only when the cell itself is bare loses the drum every time, because the cell itself is a BENCH: 6 of the 30 runs are a bench against the wall with something louder in the row behind it, and in the first build the bench answered for all six. What the pick reads is `m.deco` (the fitting kind, `_FittingKind`), `m.table`, `m.drain` and `Surf.GRATE`, all off the saved grid and the decoration objects already in every save — a room ROLE written at generation time would be null on every compound already saved, and `game.FacilityAreaGenerator` types no rooms at all (every one of them is `roomChemistryLab`). Measured: **30** over 12 rooms. A **0** means the `Surf.TILE` gate or the carries-both-ways test broke, not that the rooms are bare. **It is the one wall family that needs NO check against another builder, and the height is what buys that**: `PLACARD_Y` 4.75 spans 3.85..5.65 and clears `DECO_CABINET_H` **3.43** — the tallest thing that can share a room cell — by 0.42, so the collision `points` had to answer against `FacilityTables.runs` does not arise up there, and it never meets `EXIT_Y` 4.75 despite reading as the same band because those are LINO and these TILE. It reuses `FacilityKit.wall`'s carries-both-ways guard for `points`' reason (`slab()` insets a face by a unit wherever the wall line stops, and a fixed-width quad centred on that cell lands flush against the inset end), and the second thing that guard buys is the ROOM CORNER: two perpendicular runs meeting at one cell would each centre a 1.8-wide quad on it and cross. **Check it with a pair intersection and NEVER with a cell bin** — a quad's perpendicular coordinate sits inside the WALL cell, so two signs round one corner bin to the same key and read as a duplicate that is not there; the XZ pair test comes back **0 crossings of 30**, and it is worth re-running whenever the PLACEMENT rule moves rather than only when the geometry does — the run's middle cell made a corner crossing impossible on its own, a content cell beside one does not. Art is TWO 1k atlases and therefore TWO MESHES (`facility/placards` and `facility/placards2`, each **2x2 four square cells**, both divisions landing dead on 512 so a cell is an exact quarter and no crop rect is needed; three flips y, so a source's top row is v 0.5..1). A sign index runs 0..7 across the pair — sheet is `index / PLACARD_CELLS`, cell is `index % PLACARD_CELLS`. Sheet A is biohazard (drum-bio, a drain, a grate cell), laser (machine, machine-low), no food or drink and eye protection (both benches, split on a cell hash so a long worktop wall does not repeat one plate); sheet B is radiation (drum-rad), electrical (rack, rack-low), corrosive (drum-steel) and hand protection (shelving, bookcase, cabinet, bin). **A hazard triangle is placed AT its hazard and a mandatory blue disc is a ROOM rule**, which is the whole reason for the split and what answers the storage majority no hazard pictogram can name — 15 of the 30 nearest fittings are a bookcase, a shelf or a cabinet. Measured spread on a generated compound: biohazard 5, laser 3, no food 3, eye protection 4, radiation 3, electrical 7, corrosive 0, gloves 5 — **15 on each sheet**, and the corrosive 0 is correct rather than broken, `FIT_DRUM_STEEL` being 0 in that `batches` row on this seed. **NO lift, and this is the one entry where a fitting reads AT its wall rather than below it** — the opposite of `facility/wall-points` and deliberately: a fire point is painted steel, a placard is a printed plate. Against `facility/wall-room` 0.1375, all eight plates: 0.93x / 0.95x / 0.88x / 0.75x on A and 0.92x / 0.95x / 0.93x / 0.89x on B. Cost **+2 calls, +60 tris, +0 programs** for the family, the second call being the second sheet — and a compound with no racks and no drums emits an empty second buffer that `FacilityGeom.add` drops. The delta needs a control, because hiding the meshes in room 109 reads **+4 / +120** against 30 quads that can only be 60 triangles: **that pose renders the scene twice**, and `wall-points` A/B'd in the same pose read +2 / +44 against its known 11 quads. **A toggle delta is only a per-pass number once a known family has been toggled in the same pose.** Read it with `render.StreetPerf.lastCalls` and NOT with `renderer.info` live — `info` is reset per render and a CDP eval lands after a 1-call UI pass, reading back `calls 1 / tris 1` however busy the scene is. The +0 programs is by IDENTITY as always — `currentProgram` **64** for BOTH sheets, the same `visMasksindoor` permutation as the walls, the notice board and the fittings. **`boards` is how many lobby notice boards were emitted (`render/facility/FacilityBoard.hx`) and `front` on a `doors` row is what drives it** — one board per structure that has a front entrance, so `boards` short of the number of structures owning a `front` door means that entrance wall had nowhere to hang one. It is a MERGED mesh with no instance count, and `front` cannot be read off `look`: `FacilityModel.lookOf` collapses `FRAME_DOOR_DOUBLE` and `_GLASS` onto one painted pair, so a front entrance and a side door are the same `look`. On a generated compound: 4 `front` leaves (two entrances of two, flanking a mullion) and **2** boards. **`grime` is how many interior wall faces carry a damp band** (`render/facility/FacilityGrime.hx`) — one merged mesh, no instance count either, and since every eligible face takes one quad this IS the interior-face count. A 0 means the face predicate broke, not that the building is clean. It counts REENTRANT CORNER faces too, and that is what it is now worth reading for: a cell's own face loop skips every side its wall line carries into, and at a turn those are exactly the two sides the room's corner is made of — the notch the L leaves in its angle (`FacilityGeom.notches`). Measured on a generated compound: **400 cell faces (97/101/101/101 by direction) off 252 solid lab wall cells, plus 2 per indoor notch = 528**, against 64 notches over 42 corner cells. It was briefly an instanced-quad pass and that version shipped visibly broken; if you are tempted back to quads, read its obituary in `ContactMask`'s header first. **`sinks` is how many bench sinks stand** (`render/facility/FacilitySink.hx`) — merged-mesh blindness again, and the number is read against the bench BLOCKS rather than the bench cells: one per connected block of `m.table` that had a free EDGE cell, so it is bounded above by the block count and below by nothing. On a generated compound **24 sinks over 46 blocks and 12 rooms** (2.0 a room), off **139 bench cells of which 103 are already taken** — the generator decorates about 70% of them and forces one on every room corner, so the 22 blocks with every edge cell occupied correctly get none. A **0** in a compound with benches is the block flood-fill or the edge predicate broken; a number far under the block count is the occupancy gate, which is a real outcome. "Edge" is a neighbour count because nothing in this layer finds rects: **1** table neighbour is a run END, **2 on perpendicular hands** is a block CORNER, and 2 on opposite hands is the middle of a run and not an edge at all. The occupancy test is `m.tableTaken` and NOT `m.tableDeco != null` — the latter is null for the three frames that LIE DOWN (`Const.FACILITY_FLAT_DECO`), so it would lay a basin through a pair of gloves. **`cabinets` is how many corridor cells stand a run of storage casework** (`FacilityTables.cabinets`) — the same merged-mesh blindness a third time, and worse here, because the runs go into the SAME two buffers the generator's own benches merge into, so nothing in the scene separates the two and this is the only count of the half that is render-only. A 0 in a compound that has corridors means the run predicate broke. Gated on the RUN and not the cell, so it comes in multiples of `CASE_RUN_MIN`..`CASE_RUN_MAX`: measured on a generated compound, **30 cells over 8 runs**. Its sibling family, the corridor bins, needs no field of its own — they are appended to the `facility/trash-bin` row of `batches`, which reads **11** where the park alone gives 4. **The indoor lab kit needs no field either**: `facility/gas-cylinders` and `facility/lab-trolley` are two rows of `batches` of their own (`render/facility/FacilityKit.hx`), the first glb props in the compound that stand INDOORS. They are gated on `Surf.TILE` where every corridor family above is gated on `Surf.LINO`, which is the whole of what keeps them from ever colliding with the casework, the bins or the signs — no shared claimed-cell list and no ordering between builders — so a 0 in either row means the room-wall predicate broke and not that the rooms are full. Measured on a generated compound: **5 racks + 4 trolleys**, off a `KIT_MAX` of 10. Note that a batch's `count` here is the PLACEMENT count and not what is drawn: `render.Models.cull` packs only the visible instances into the mesh each frame, so `mesh.count` read off the scene is a per-frame number and `instanceMatrix.count` is the allocation. **`exits` is how many lit exit signs are hung** (`render/facility/FacilityExit.hx`) — a merged mesh again, and it covers TWO families that nothing in the scene separates: TERMINAL signs over the inside face of a door that leads outdoors, and DIRECTIONAL signs on the corridor walls the escape route runs into. Read it against the two things that generate it. The terminals are one per exterior door with circulation behind it, so a count under the number of `doors` rows that lead outside means the corridor-lino test broke — the hangar shutter is the one exterior door that correctly has none, tarmac one side and concrete the other. The directionals are one per approach wall that survives `EXIT_APPROACH`, which is the ONLY density knob and the one that separates a wall you walk AT from a wall you walk PAST: a corridor here is 2 cells wide and the route flood reaches one lane a step before the other, so at 0 every straight run reads as an approach and the compound takes **127**; at 2 it takes 24, at 3 fourteen, at 4 nine. A directional is also dropped where the wall it would hang on already carries a terminal sign one cell along it — the generator cuts an entrance as two leaves flanking a MULLION, so without that test the mullion took an arrow that had to pick one of two doors 4 units away that both already have a sign. Measured on a generated compound: **16 signs = 6 terminal + 10 directional** against 18 doors, 6 of the 10 mirrored (the arrow points along +u as drawn, and a sign pointing the other way flips u). The two halves are also separable off the mesh itself if you need them — the atlas v of a quad's first vertex is ≥ 0.5 for a terminal. **`patches` is `{ tex, lawn, cells, strong, tufts }` — the park's overgrown-grass overlay (`render/facility/FacilityLawn.hx`), and `strong` is the only number it can be TUNED on**: `cells` is how many lawn cells were marked, but what the player sees is the coverage FIELD, and what shows through a near-uniform one is just the art's own ~41% opacity — grain over the whole park, which the wilderness pass misjudged by eye twice. `strong` is the share of the lawn's own bounding rect whose mask clears `alphaTest`, read live off the retained canvas; it is deliberately measured over the PARK and not over the 1024² canvas, which spans the whole 400-unit area rect and would report a fraction of a percent however overgrown the lawn was. Shipped at **20.3%** (6 seeds, 17 cells on a generated 12x25 park). **`roof` is `{ parapets:[{structure,skipped,cells,quads}], props:[{col,row,kind,structure}], hatches }`** — the roofline and what stands on it (`render/facility/FacilityRoof.hx`). `quads` is read straight off the buffers the emitter wrote, so it cannot drift from the geometry, and `skipped` reads off `hangar`: the hangar has no parapet and no props by construction, so a non-zero row there is the bug. A prop's `structure` is not decoration — it is what decides whether the prop draws at all, because a roof batch is culled with a MASK keyed on that structure's `reveal`, so one keyed to the wrong deck vanishes when the player walks into the building NEXT DOOR. **`roof.hangar` is `[{structure,span,rise,radius,arcDeg,seg,quads,gables,ridgeAlongX,ridge}]`** — the barrel vault, as the numbers it was DERIVED from rather than as geometry, because an arch is the one roof here a screenshot cannot check at all. Whether the section is really a circle segment is `radius` against `span` and `rise` (`radius == (span/2) / sin(arcDeg/2)`, and `arcDeg == 2·2·atan(2·rise/span)` in degrees); whether it is the shallow arc it is meant to be is `arcDeg` against the **180** a half-round barrel would read; whether the ridge took the long axis — which is what decides which pair of walls gets a gable crescent — is `ridgeAlongX`. `quads` is `seg` (the arch, in the fading deck) and `gables` is `2 × seg` (the two crescents, which are cladding and live in the structure's own wall mesh), both read off the emitter so neither can drift from the geometry. **`ridge` is there because `span` alone cannot catch a vault fitted to the wrong rect**, and that is not hypothetical: the vault used to take its box from `st.ox1..ox2`, the flood fill's bbox grown by a cell, and a door cell is ordinary lino floor so the fill ALREADY reaches into the wall ring at a doorway — the hangar's own side door took `ox1` one cell too far and the roof overhung that gable by 4 units with `span`, `radius` and `arcDeg` all still reading correctly. Attached on area build.
- **`window.__progs()`** (`render/View.hx`) — live shader-program cache as `cacheKey` strings (`renderer.info.programs`). Diff the array before/after an action (e.g. first gas burst) to see which material permutations the driver compiles on first use — those first-use compiles are the frame hitches. Attached in `ensureCore`.
- **`window.host`** — Electron preload bridge (`save`, `settings`, `profile`, `mods`, `shell`, `debug`, …). `contextIsolation:true, sandbox:true` — no node APIs in the renderer.
- **`host.minimize()` / `host.restore()` / `host.isMinimized()`** — park the window out of the way through a build and wake it for the next measurement (`electron/preload.js` → `host:window:*` → `MainElectron.hx`). **These are MAIN-PROCESS handlers, so `make reload` does NOT pick them up — the app has to be restarted** (`make main` builds them). Two things were measured on this rig (Electron on the Windows host, CDP across the WSL boundary) and both contradict what you would expect from the backgrounding rules below:
  - **A MINIMISED WINDOW COSTS NOTHING FOR INSPECTION.** `evaluate_script` answers normally — an eval that spans its own `minimize()` returns fine — and `take_screenshot` returns a REAL, CURRENT frame: captured minimised vs captured after `restore()`, 230 luminance levels both, mean |d| **0.22** and max **2** over 40,150 sampled pixels, i.e. animation jitter and nothing else. So parking the window through a build is free, and reading it while parked is safe. (The compositor throttle is a separate matter and still bites: it wrecks TIMING, not capture — never trust `perf.lastGpuMs` or an fps read taken while the window is down or unfocused. See the weak-GPU rules below.)
  - **`select_page({bringToFront:true})` DOES NOT UN-MINIMISE IT.** Measured: minimise, `bringToFront`, and `isMinimized()` still reads `true`. `bringToFront` raises and selects a window that is merely buried; a minimised one stays down. **`host.restore()` is the only wake** — and since page calls work while minimised, calling it is not a chicken-and-egg problem. It calls `focus()` too, deliberately: `restore()` alone can leave the window unfocused on some window managers, and an unfocused window throttles to ~1fps, which silently corrupts any timing measured right after the wake.

## In-engine debug keys

- **In-engine debug keys** (street-debug mode, backtick): `1` lighting/bloom, `2`/`3`/`4` ambient/hemi/moon fill, `5` lamp spotlights, `0` all lights, `6` emissive, `7` shadow SAMPLING A/B, `8` reset perf peak, `9` draw-call breakdown dump (traced + copied to clipboard), `M` force every lit material matte. `7`/`8`/`9`/`M` + the perf HUD live in `render/StreetPerf.hx`; the console `perf street` toggle (`render.Actors.DEBUG_PERF`) shows the same HUD **without** locking game input, so it is the one to use while walking (debug mode owns the keyboard for the fly-cam).
- **Chasing a "why is this prop shiny/bright" art bug — `1` cannot answer it, `M` and `6` can.** `1` is WYSIWYG **albedo**: it hides every light and adds a full-bright ambient, so specular (which only exists under an analytic light) is gone by construction and whatever still looks wrong under `1` is the base-colour map. `M` clears metalness/roughness **and their maps** — the maps are what matter, since roughness/metalness are factors the map multiplies, so a mapped material stays glossy when only the factor is cleared. `6` isolates emissive. Baked glb props used to be the usual culprit — a PBR export lands at metallic 1 / roughness 1 with an MR map and read as chrome against the flat art — but a prop no longer HAS a specular path (`Models.toLambert`, see the models section), so `M` and `dropMR` are now no-ops on everything but the habitat props, and a prop that still looks wrong is its base-colour map: `baseColor` / `lift` in `art/models.json`, not shader work.

## Measuring on the real hardware

- **Measuring on a weak/integrated GPU** — the numbers lie unless you do all of this: **pin the camera** (`parasiteHx['render.Tools'].freeCam.lookFrom(...)` — `Tools.freeCam` is a static, so one pose reproduces exactly across reloads AND rebuilds; verify by `calls=`), **interleave A/B/A/B and take the MEDIAN** (means get destroyed by outliers — one run turned a real −19% win into a bogus −7% loss), **warm the shader permutations first** (keys `5`/`7` change the program key; the first toggle compiles a new set), and **never compare across sessions** — an integrated Radeon switches power state mid-run and the *identical* pinned frame was measured at both 11.61ms and 4.06ms. Shares (`1 − off/on`) survive clock drift; absolute ms do not. **The game window must be FOCUSED and in the foreground** — backgrounded, the compositor throttles to ~1fps and the timer query spans the whole idle gap, so `GPU` reads ~**1015ms** and an A/B comes out *inverted*. Any scripted sweep should filter samples (`GPU < 100`) and check the topbar fps before trusting a single number.
- **GPU-side (fill) A/B keys** — for when `GPU=` exceeds `submit=` and the frame is fragment-bound, which the draw-call keys above cannot see: `V` cycles the render scale (1.25 / 1.0 / 0.75 / 0.6, traced as `[render-scale]`; `View.setRenderScale` drives `renderer` + `composer` together), `Shift`+`1` toggles **bloom alone** (plain `1` flips lighting and bloom together), `Shift`+`5` toggles the **light cones alone** (plain `5` hides the 12 spotlights *and* the cones, so it cannot separate the per-fragment light loop from the additive cone overdraw). Return to baseline between measurements — `5` and `Shift`+`5` both touch the cone group.

# 3D models: image → glb → the game

`generate_image` → `image_to_3d` (TRELLIS 2 on Runware) → an entry in `art/models.json` →
`make models`. Loaded on demand; the `3d-art` skill triggers it. `CLAUDE.md` keeps only the guards
that fire before this doc is opened (a box is not a prop; warm the new glb path).

Every number below came out of [`tools/propstat.py`](../tools/propstat.py) and was paid for by
shipping the mistake once. **New findings go here, not into `CLAUDE.md`.** One bullet per lesson,
the number that proves it inline. When a lesson invalidates an old bullet, replace it rather than
appending a second.

See also [`3d-textures.md`](3d-textures.md) (reference images and tiling art) and
[`3d-render.md`](3d-render.md) (what a prop costs in the frame).

## The pipeline, and the tool every number comes from

- **A new prop is generated, not hand-modelled** — unless its brief is a NUMBER, which is the Blender-over-MCP route below. Four steps: `generate_image` (gpt-image-2) → **`image_to_3d`** (the `runware-trellis-2` MCP, Microsoft TRELLIS 2 on Runware) → an entry in `art/models.json` → **`make models`**. ~$0.03 and a couple of minutes per prop. The MCP server lives at `~/git/runware-trellis-2-mcp` (one tool, node/TS, `pnpm build`); `RUNWARE_API_KEY` comes from the shell env, and its default output dir already resolves to `<git root>/models-src`, so **do not `mv` the glb** — it lands where `make models` looks.
- **Every number the rules below are written in comes out of [`tools/propstat.py`](../tools/propstat.py), and it takes either end of the pipeline.** `python3 tools/propstat.py <prop>.glb` reports tris, split ratio, connected components + largest share, bbox `widest/height`, albedo (whole-atlas AND sampled at tri UV centroids), texels-per-triangle with the `tex` that lands in band, and the MR verdict — each with a pass/REJECT read, and a starting `baseColor` or `lift` when the bake is out of the 46-52 family. `<ref>.png` reports subject value against the p50 69-77 that bakes correctly, frame margin, bbox aspect and the backdrop's real colour. `<ref>.png --lift 70 -o out.png` and `--fit 80 -o out.png` apply the two in-code reference corrections below. Run it on the source before wiring a prop in, and on the built glb after `make models`.

## Hand-modelling in Blender over MCP

Most of this was ported from the `memento` project, which paid for the numbers; the port, the pipeline below and the workstation entry in `3d-changes.md` are this repo's own. The `blender` MCP is registered at **user scope**, so it is already present here and there is nothing to install per project — `claude mcp list` is the check, and it drives the Blender the user has OPEN (it is a live session, not an offline exporter: what the script builds appears in their viewport).

**THE ROUTE, END TO END** — the workstation (`models-src/facility/computer_build.py`, three glbs at 268/116/44 tris) is the worked example and every step of it is in that file:

1. **The build is a SCRIPT in `models-src/`, never hand-clicking.** Constants at the top copied from the game's own (`FacilityStyle`), one function per part, an explicit per-face UV table, `export_scene.gltf` per object, `save_as_mainfile` last. Run it with `exec(compile(open(p).read(), p, "exec"))` through `execute_blender_code` — so a fix is an edit to a file in the repo, a re-run is one call, and nothing is a lost click. `models-src` is a symlink to a Windows path, so Blender reads and writes it directly.
2. **Build with QUADS — `bmesh.ops.create_cube`, never `convex_hull`.** The hull comes back triangulated, and any per-face UV map then lays the whole cell over each half of every face: a diagonal seam across every surface.
3. **UV onto the game's OWN sheet and let the exporter pack it — but GENERATE THE ART FIRST, because ~90% of new props need new labels.** Reuse is the instinct and it is usually wrong: an existing label was fitted to ANOTHER object at ANOTHER scale, so it arrives as the wrong weave at the wrong repeat, and the per-face rule ([`3d-geometry.md`](3d-geometry.md)) means one object wants two or three labels of its own. The lounge sofa was planned wearing `bench-body` and the table wearing `desk-top` and the user rejected it on sight; it is the same mistake that shipped 9 of 38 props grey. **Reuse only when the new piece IS the old material at the same scale** — a second shelf of the same steel, a drawer front on the same cabinet. Otherwise: one packed gen (4 × 512 in a 1k sheet is ~$0.055 for a whole prop's worth of faces) and `art/textures.json` entries, **and ask the pack-vs-solo question first**. A prop that genuinely reuses an existing texture carries NO `baseColor`/`lift`/`sat` in `models.json` — that art is already fitted, and a knob here is a second correction over a fitted one. Crop each cell to its measured CONTENT, not its nominal rect ([`3d-textures.md`](3d-textures.md): an authored cell is often an object on a plate). **`tools/modelsheet.py` packs several BUILT labels into one sheet** for a prop replacing an emitted fitting, and `--repeat u x v` bakes the emitter's own tiling into each cell — a packed cell cannot wrap, so the repeat has to live in the pixels.
4. **`"tris": -1`** — it was authored AT the budget, so `propstat`'s split / UNDECIMATABLE / COMPONENTS lines are TRELLIS gates reading a hand-made assembly (a foot, a neck and a shell is 3 components and is not a blob cloud). Then `make models`, the `RenderConfig.MODELS` path, the batch and the warm row, exactly as a generated prop.
5. **`buildlib.check(ob)` before the export is accepted, and a nonzero count is not finished.** An assembly of interpenetrating boxes has THREE faults and a quad emitter could not make any of them. A **hole** (an edge not shared by exactly two faces) and a **shared plane** (co-facing faces closer than 0.01 with overlapping ground — NEAR-coplanar, because 0.005 shimmers as readily as 0) are the two at either end of the same decision: keep every face and pull the PLANES apart; deleting the buried ones is what shipped both server racks full of holes. Pairs sharing a vert are skipped (an inset ring is four coplanar faces that tile) and `-z` is skipped whole, per `FacilityRoof.box`. **`islands` is the third and it must read 1** — a shell whose bounding box misses every other shell's is a piece of the model standing in mid-air, which neither of the other two can see, because each is about a pair of faces and this is about a piece that has no pair. It is NOT a component count: a model on this route is disjoint shells by design (the bench desk is eight, the printer eleven), so the test joins any two whose boxes touch AT ALL and reports what is left over. Four shipped before it existed and every one was reported from the game by eye: the bench's cable tray hanging 0.19 under the worktop with its ends 0.25 clear of the leg frame, the desk mug's handle ending **0.002** outside the wall ("the handle is not attached"), the desk plant as **eight** islands — a crown floating 0.055 over the soil and six leaves floating 0.019 over the crown — and the webcam's lens ring 0.003 in front of its head, which nobody had noticed at all. Abutting counts as joined, so a foot under a pedestal is not a false alarm; a gap you chose still reads as a gap, because a trinket's whole fault was 0.002 wide.

**`models-src/facility/buildlib.py` IS THE SHARED HALF OF THAT ROUTE**, and a new model should be a shape table and nothing else. What it gives you, and the rule attached to each:

- **`tube(profile, n, shape=None)` — a lathe over a `(radius, z)` table.** What `create_cone` cannot state: a drum's rolling hoops, a bottle's shoulder, a pot's rim and a basin's bowl are all a radius that CHANGES up the piece, and that is what a round prop reads as at this camera — steps catching light, not roundness. `shape` takes any cross-section (`roundrect`), so a drop-in sink is the same lathe as a barrel. **THE PROFILE RUNS COUNTER-CLOCKWISE ROUND THE SECTION** in the (radius, z) half-plane: for a can that is bottom to top, for a VESSEL it is out to the rim, over it and back DOWN the inside to the floor, so a mug's coffee and a basin's bowl are part of one closed surface. Run it the other way and the piece comes back inside out.
- **`sweep(path, r, k)` — a ring carried along a path**, for a mug handle or a tap's gooseneck. The frame is PARALLEL-TRANSPORTED and must be: derive it per ring from a fixed up-vector and it flips wherever the path crosses that vector's plane, which bridges the two rings either side of an apex into zero-area bowties.
- **`lathe_uv` / `disc_uv` / `flat_uv` — write UVs directly, and every one of them exists because `unwrap`'s bounding box lied.** `unwrap` lays a face over its OWN bbox into the whole of a rect, and that is wrong three ways: a CAP lands wherever the art's disc happens to sit in its cell (the drum's lid art is 21 px high and 7 px left of centre in a 512 cell — reported as an off-centre top); a side face's widest two axes swap quadrant by quadrant, so a cylinder's wrap MIRRORS round the barrel; and widest-two is right for a TALL box and wrong for a FLAT one, which put a paper-stack's horizontal layers across a tray's flats instead of up its edge. `flat_uv` is for a piece skinned BEFORE it is moved — a leaf cut flat, then pitched and turned.
- **A PIECE MOVED AFTER `unwrap` MUST BE MARKED DONE: set `f[layer] = -1` on every face before the swing.** `unwrap`'s bbox branch maps a face but does not mark it, and `finish` then unwraps every face again over its NEW, diagonal bbox. The gun cabinet's open door leaf, swung 100 degrees after its unwrap, showed ARMORY mirrored in game. `gun_cabinet_build.py` and `wall_cam_build.py` (the pitched head) both mark the faces before they move.
- **BREAK THE ARRISES AND SMOOTH THE TURNED FACES BY DEFAULT — both are opt-OUT, not opt-in.** `finish` hands shading to the builder and `box` returns a hard-edged cube, so a script that says nothing ships a prop of razor arrises and faceted cylinders. Three corp scripts said nothing (`appliance_build`, `clutter_build`, `desk_build` — nine props: cooler, printer, mug, bottle, plant, webcam, bench, blade leg, bin) and the whole set came back reported as hard and faceted in one pass. The cost is known and it is the only argument against: one segment of chamfer is ~**40 triangles a box** (the printer went 132 → 484, the cooler 184 → 524 at two segments), so opt a box OUT when it is buried or under ~0.12 across — the bench's modesty panel, its cable tray and its 0.11 leg sections take no arris and its worktop, pedestal and drawer front do. A lathe has no such excuse: `f.smooth = True` on the side bands is free.
- **`chamfer` — break the arrises as GEOMETRY, never with a bevel modifier.** The modifier interpolates each new strip's UVs between the two faces it joins, so on a packed sheet a strip between a face on cell 0 and one on cell 1 sweeps diagonally across the whole image. Build the strips before the unwrap and tag them with **THE PIECE'S OWN RECT**, `flat=True`, which aspect-fits the strip and hands it the art at the density of the faces it breaks. **NEVER a separate edge / plain / galvanised cell** — the third report of this was the store rack, whose orange uprights came back outlined in grey on every arris because the caller passed a galv index for the strips; an arris is a LIT EDGE of the thing it belongs to, not a different material stuck along it, and the only cases that survive scrutiny are a piece genuinely trimmed in another metal. **Shade ONLY the strips smooth** — shade the flats too and every large face picks up a corner gradient, because a bevel's corner normal tilts by the same angle however narrow it is.
- **SMOOTH-SHADE EVERY TURNED FACE, and count sides for the SILHOUETTE only.** `finish` used to force every polygon flat, which is a cylinder's worst case: the facet count IS the read, and it made "twelve sides is a measured floor" look true. Smooth, sides buy the outline alone — sixteen is round at trinket scale and twenty has margin on a 1.2-diameter drum.
- **THE FIT'S WINDOW SIZE IS THE DENSITY AND IS NOT YOURS TO CHOOSE — ITS POSITION IS (`buildlib.at`).** `unwrap` crops a rect to `faceExtent / scale` on each axis so every face of a model lands on the same texels per world unit; a 3.6 x 0.16 rack beam therefore asks for 440 x **19 px** of a 512 cell, and 19 px is not a fault — the beam is 19 texels tall. The fault is that the crop is taken about the rect's CENTRE, and the centre is where a sheet draws the cell's feature (a punched column, a fold line, a hazard diamond), so the one thing a narrow face cannot render is the one thing it lands on. **NEVER PRE-CUT A RECT A FITTED FACE WILL USE** — the crop then applies to the CUT, and a 56 px band times a 3.8% fit came out a **two-pixel sliver** stretched along 3.6 units, reported from the game as mapping to a tiny sliver of a big texture. Move the anchor instead. Same rule turned: a LATHE's bands share one cell along the profile (`lathe_uv`'s `v0`/`v1`) rather than each fitting its own slice about the centre.
- **A SWEPT ROD, A CAP AND A TINY FACET ALL NEED A SWATCH OFF THE CELL'S MIDDLE, and the reason is the GUTTER as much as the art.** `unwrap` axes 2 lays the whole cell over each face, so every one of them runs out to the cell's own edge — and a prop at `tex` 256 has the sheet's 2 px pad down to 1 px, where mip level 1 has already mixed the neighbouring cell in. The desk mug shipped its handle that way and the game reported BLACK LINES on it: 80 facets each spanning u/v 0.004..0.496 of a ceramic cell sitting directly above a charcoal one. Same rule for a CAP, which `disc_uv` maps in PLAN: the cooler's bottle cell is painted as vertical flutes (23/107/158 in the seams to 100/190/226 on the highlight) and the dome wore them as stripes laid flat across the one face this camera reads. Crop a central patch measured for flatness — the cooler's is x 88..112 of the 256 cell at sd 4.5 against the cell's own 16.
- **A plain swatch is STRETCHED over whatever face takes it, so crop it small enough to be UNIFORM.** A 0.4 × 0.1 crop of a striped cell arrives as stripes across a tray's lid. **And it is a FITTED VALUE, not a free pick** — a plant leaf's 0.014-thick edge took the face's own crop and every blade had a pale rim, then took the DARKEST uniform patch in the cell and every blade came back with a black outline round it. Aim at a fraction of the neighbouring face's own luma (82% there) and fix the GEOMETRY that made the swatch visible in the same pass, or the next correction overshoots the other way.

- **The MCP is fine and the PORT is where it fails, on this machine with a specific error.** `[WinError 10013] An attempt was made to access a socket in a way forbidden by its access permissions` on Start is NOT a firewall and NOT a busy port: **9876 falls inside a Hyper-V reserved TCP range** — `netsh.exe int ipv4 show excludedportrange protocol=tcp` listed `9807-9906` here — so the addon's `bind` is refused. Fixed by moving both ends to **19876** (addon Preferences → Add-ons → MCP → Port, plus `BLENDER_MCP_PORT` / `_DEFAULT_PORT` in `blmcp/tools_helpers/connection.py`). Freeing the reservation instead costs `netsh int ipv4 set dynamicport tcp ...` as admin AND a reboot. **A `/mcp` reconnect may re-use the cached config**, which is why the server-side default was patched too; `netstat.exe -ano | grep <port>` against Blender's PID is the check that the addon is really listening.

- **A fourth route, and the test that picks it is DIMENSION.** TRELLIS for a silhouette, a tiling texture for a surface, emitted quads for axis-aligned slabs ([`3d-geometry.md`](3d-geometry.md)) — and Blender for anything whose brief is a NUMBER: an exact height, a parametric splay, a boolean cut, a part that has to land on a `FacilityStyle` constant. What it does NOT buy is cheapness. A bar stool modelled this way (seat top 700 mm, legs splayed 8.2°) landed at **1,966 tris** against that project's own emitted rebuilds at **22-34**. Blender guarantees the dimensions; the triangle budget still has to be argued separately, and `propstat.py` still judges the glb. **AND THERE IS A FIFTH THING THIS TRIAGE HAS TO COVER AND DID NOT SAY A WORD ABOUT: a 2D CLUTTER ATLAS.** A PACK64 cell ([`3d-textures.md`](3d-textures.md)) is the right route for a small FLAT thing lying on a surface and costs a 64th of one draw call, and it is a lie for a cell whose read is a round or upright silhouette — a mug, a bottle, a potted plant, a webcam on a stalk — because a top-down cut-out has no side. Those go to Blender like anything else whose brief is a shape, at one instanced batch each: `corp/desk-clutter` gave up six such cells for **four** glbs at 120-280 tris (models-src/corp/clutter_build.py), paired so one lathe serves two cells. Judge it per CELL and not per sheet — the other 58 cells of that sheet are correct as decals.
- **The add-on binds `localhost` on the machine BLENDER runs on, so an MCP server inside WSL can never reach a Blender on Windows.** `mcp_to_blender_server.py`: `DEFAULT_HOST = "localhost"` → `sock.bind((host, port))`. Run the SERVER on the Windows side over interop rather than bridging the socket — `claude mcp add blender -s user -- uv.exe run --project C:/Users/mmm/blender-mcp blender-mcp` (`uv.exe` resolves through the WSL interop PATH). **No `netsh portproxy` and no firewall rule** — both are what you reach for after assuming the server must live in WSL. A `.mcpb` bundle is a zip: unzip it and `manifest.json`'s `server.mcp_config` is the command to register.
- **Blender's "Allow Online Access" gates the add-on server** — without it, start fails with "Online access must be enabled in the system preferences". Autostart is a pref (`use_autostart`), off by default, so a running Blender is not a listening Blender.
- **A WSL-side port probe proves nothing here either**, the same trap as the CDP rule in `CLAUDE.md`: `nc -z 127.0.0.1 9876` came back refused and `172.18.208.1:9876` timed out with Blender plainly listening. `tasklist.exe` and `netstat.exe` are the test.
- **A tilted cylinder's flat end cap sinks below the floor by r·sin(θ), and the correction goes STALE the moment the radius changes.** Legs at r=18 mm on an 8.2° splay sank **2.6 mm**; after tapering the feet to r=13.5 mm that same lift left them floating **0.66 mm**. Never carry a hardcoded offset — measure `z_min` on the evaluated mesh and subtract it.
- **Measure the EVALUATED mesh (`o.evaluated_get(depsgraph)`), never the base one.** A bevel took a seat 289 → **577 faces** and shaved 1 mm off the rim, so a 12 mm nominal dish measured **11 mm**. The tri count comes off the same call: `sum(len(p.vertices) - 2 for p in me.polygons)`.
- **Primitive defaults are where the triangles go.** `primitive_torus_add` defaults to 48×10 = **960 tris** — **40%** of that whole stool, for a plain tube. Hand-swept at 32×8 it is **512** with radius and z-span re-measured identical. bmesh has no torus op; sweep the minor ring round the major circle.
- **`bpy.data.is_dirty` reads TRUE immediately after `save_mainfile`** — the operator pushes an undo step that re-marks the file — so it is not a post-save check. Compare the on-disk size.
- **Stacked `view_orbit` calls accumulate ROLL.** Three in a row produced a screenshot of an apparently tipped-over stool whose feet measured `z_min = 0`. Set `region_3d.view_rotation` from a Euler instead, then `view_selected`.
- **A screenshot taken while EEVEE compiles comes back EMPTY** — blank viewport, "Compiling EEVEE engine shaders" in the header. Re-shoot. And **metallic 1.0 wears the preview HDRI**: the same steel legs read brassy in one frame and grey-green in another. That is the environment, not the material.
- **Writing a file through `execute_blender_code` trips the auto-mode classifier** and needs an explicit approval on the retry. It is not a Blender error, and saving is the only step that hits it.
- **A BURIED JOINT WITH FLUSH FACES IS A SHARED PLANE, and `check` counts every one.** The exec photo frame (`models-src/corp/exec_trinket_build.py`) was four bars buried into each other at the corners with their fronts, backs, tops and bottoms flush: **coplanar 18**. Staggering the backs of the print and the bars took it to 6; the stiles made 0.012 proud of the rails on every side (deeper and taller) and the print widened into the stiles past the rails' ends took it to **0**. Stagger by MORE than `check`'s 0.01, and stagger every axis the joint shares, not just the one you can see.
- **Ground a LEANED piece by measuring, never by typing the drop.** Rotating a slab back about its bottom edge swings the front edge below z 0 (-0.0036 on the 14 deg frame). The trinket script's `ground(bm)` moves every vert by `-min(z)` after the lean, so a dimension change cannot leave it stale — the tilted-cylinder bullet above, in general form.
- **`check` NOW REPORTS UV DENSITY — `texel_off`, `texel_worst`, `spots` — because every geometry gate read 0 on furniture whose UVs were wrong everywhere.** The exec set shipped with `finish(...)` given no `scale` (every fitted face cropped its cell to its OWN bbox), `chamfer` left non-`flat` (a 0.03 arris got the whole cell across it: 7x the flats beside it), cushion rims on ONE texel and a lathe wrapping the whole brass cell round a 0.9 column (13x). Reported from the game on every edge of every piece. First fix, ONE `unwrap` `scale` for the family: consistent, and **wrong** — the scale has to be the biggest face (the 11.76 desk; anything wider clamps and stretches), so every chair dropped to 22 texels a unit, reported as "the same but very shit density". **The fix that holds is to TILE INSIDE THE CELL: `buildlib.grid_cut(bm, s)` then `tile_uv(bm, layer, rects, s)`** — cut the mesh on an `s` world grid so no face crosses a line, project each face on the two world axes its normal is least along, map its grid cell's 0..1 into the atlas cell and MIRROR every odd tile (bookmatched, so the art need not tile). Axes 8 turns it a quarter (brass brushed down a leg). At `TILE` 2.0 and 512: **128 texels a unit on everything**, `texel_off` 0, worst 1.19x (tilted arrises); tris 516 -> 1,260 on the 3x2 desk. Chair `texel_off` went **208 -> 0**. **Read `texel_off` on every build, as you read `coplanar`, and look at the density in game: the gate proves consistency, not adequacy.**
- **`grid_cut` SPLITS A WHOLE LABEL, so lay axes-7 faces AFTER it.** The cut bisects every face that crosses a `TILE` line, and `unwrap` maps an axes-7 face's rect over EACH piece, so the vending machine's 1.36 x 2.04 glass came out as four copies of the machine (`check` texel_worst **13.87**). `models-src/corp/kitchen_build.py` queues its labels (`label` -> `LATE`) and `done` boxes them after `grid_cut` + `tile_uv`, then tiles their edges in a second `tile_uv` pass. The same thing hit nothing in the exec set only because its two labels were smaller than a tile.
- **BUILD EACH PIECE THAT GETS CUT IN A BMESH OF ITS OWN, then append it (`bm.from_mesh`).** A vertex set taken before `bmesh.ops.bisect_plane` is not a stable fence: `models-src/wild/rock_build.py` chipped blob N of a multi-blob rock with a geom list built from "verts not in the set taken before this blob", and the cut reached the earlier blobs anyway. `check` read **26 coplanar pairs at gap 0** on the cluster, every one a sliver of an old blob lying on a new cut. Single blobs read 0, which is what pointed at the fence.
- **A FORK OFF AN n-SIDED LIMB ROOTS UNDER THE PARENT'S INRADIUS, NOT ITS RADIUS, and a fork off its TIP needs a knee.** `models-src/wild/deadwood_build.py`'s bare tree was reported with holes at the forks, and both causes were geometry that `check` cannot see, because every piece is closed and the joints overlap. First, a 6-sided section's flat faces stand at **cos 30 = 0.866** of its radius and two limbs twist out of phase, so a child rooted at 0.9 of the parent's radius pushed its root-cap corners through the parent's faces: 17-83% of those caps' verts were buried. 0.78 buries them all. Second, a child continuing off the parent's tip leaves a wedge on the outside of the bend where both end caps show. Sleeving the child fatter and further back made it worse. A rounded bark DOME on the parent fills the wedge as a ball joint would. The test that found both is a BVH ray-parity check of each end cap's verts against every other shell, and only the free broken tips should come back exposed.
- **SIZE A DESK TRINKET OFF THE DESK, not off the real object's centimetres.** A nameplate built at 0.74 wide stood on an 11.76 desk read as a crumb from the game camera; a real one is about an eighth of its desk, so both trinkets batch at TWICE their modelled size (`CorpStyle.PLAQUE_H` / `PHOTO_H`). The model's own proportions are what matter; its absolute size is the instancing height, which is one constant.

## The reference image

- **The reference sets the COMPOSITION; the settings set the TOPOLOGY. Do not blame one for the other.** ONE object, centred, whole, clear of the frame edges, on the same flat solid grey `#5a5d63` the texture pipeline falls back to (no ground plane, no cast shadow, no horizon), with the canonical **`style_prop`** string appended verbatim — the OBJECT string, never `style`, which is the surface one (see the chroma bullet under Materials). Keep the grey here — gpt's `background:"transparent"` is untested as a TRELLIS reference and TRELLIS wants a uniform backdrop to segment against. A cropped or cluttered reference comes back a blob. **And "three-quarter" is about the ATLAS, not only the silhouette — shoot it ISOMETRIC, from above one corner, so the TOP face and a SIDE face of every part are both in frame.** `facility/barrier` is the entry that proves it: a near-flat side elevation gave a perfectly good MESH (2 components at 86.2%, 1.22x split, correct proportions) and a **junk texture** — the arm's top and back faces are simply not in a side view, so TRELLIS invented them and the baked hazard stripes came back bleached and disagreeing chart to chart. Re-shot isometric at ~35° from one corner, with the stripes stated to wrap continuously over the edge from top face to side face, the same object baked a coherent atlas. A face the reference never shows is a face the generator hallucinates. **What the reference does NOT decide is how the surface fragments** — that headline used to read "the reference decides the mesh, far more than any setting" and a one-variable probe killed it: the *same* image that produced 96 disconnected blobs came back **1 component at 100%** on the corrected settings alone. The tidy story (every dark gap in the art becomes real air) fits the data and is still wrong. When a mesh comes back fragmented, re-run the settings before repainting anything.
- **Three reference fixes that are free, and one gpt defect they cover.** A reference can be corrected **in code** instead of re-prompting — a gamma on the subject (`--lift`), a shrink off the frame edge (`--fit`), and a re-lay on a truly flat backdrop, all of which hold the composition fixed so the next bake differs by *one variable*. That is how "is it the value or the shape?" gets answered for $0.01 instead of $0.24, and it is the answer to propstat's own **"TOUCHING THE EDGE, comes back a blob"** gate: gpt lays a long diagonal object corner to corner however loudly the prompt asks for a margin, and a re-roll gives a *different* composition where `--fit 80` gives the same one, smaller (`facility/barrier`: margin l 13 r 2 t 0 → 89/79/187, scale 0.947). They also fix a defect worth knowing about: **gpt paints a vignette**. Asked for flat `#5a5d63` (90/93/99) it delivered a backdrop measured at **82/86/91** with a gradient across it — darker than requested, which narrows the subject/backdrop margin TRELLIS segments on exactly when a dark subject needs it widest. **Key the correction against the backdrop gpt ACTUALLY PAINTED, not the nominal `#5a5d63`**: 42 apart in propstat's metric is past the soft key's foot, so nominal keying leaves the whole backdrop ~24% opaque — invisible when `lift` re-lays the WHOLE frame, and a hard rectangle border when `fit` pastes a sub-rect.
- **A BOX IS NOT A PROP — before generating anything, ask whether its silhouette is worth generating at all.** If the object is axis-aligned slabs (a kiosk, a bench, a cabinet, a low wall, a skip), EMIT IT: [`render/facility/FacilityGeom.hx`](../src/render/facility/FacilityGeom.hx) has public `face` / `pane` / `cap` / `add` / `geom`, and [`FacilityTables`](../src/render/facility/FacilityTables.hx) and [`FacilityEntry`](../src/render/facility/FacilityEntry.hx) are both worked examples. What you get is exact proportions, the game's OWN tiling textures at full texel density (a prop's atlas is finite and spread over the whole model, so its density falls as the prop grows — see the texels-per-world-unit bullet below), and no unwrap lottery. Measured on the guard booth, generated first and rebuilt second: **7,431 tris → 34**, and the glb was a `propstat` REJECT anyway (40 components, largest 58.1%, 3.14× split, albedo 91/97/104) because a mesh generator handed a rectangular box returns a blob cloud of one. The same job also deleted a `models.json` entry, a `texSrc`, a generated emissive map and a warm row.
- **But "is it a box" is the wrong test, and it let the wrong thing through once. Ask instead: is this object carried by its SILHOUETTE or by its SURFACE?** The boom barrier beside that booth was exempted on the box rule — an arm, a counterweight and a cabinet genuinely IS more shape than a kiosk — and it was still wrong, because a boom barrier is not carried by its outline at all: **it is carried by its hazard bands**. The bake returned orange chevrons on tan where the reference painted red on off-white, and there is no fix on that path (`baseColor` is a per-channel MULTIPLY and can never put back contrast the generator merged away). Rebuilt as geometry with the bands as a tiling texture: **3,098 tris → 22**, and `propstat` had scored the glb almost exactly as it scored the booth (3 components, largest 65.9%, 2.07× split, albedo 145/125/105). A silhouette is what a mesh generator is for; a stripe, a rhythm, a material is what a tiling texture is for — it cannot lose contrast, cannot smear, holds density at any length and costs $0.01 to repaint. **Two smells that the surface is doing the work**: the `models.json` note is arguing for a hand-fitted `baseColor` off the family, or the object's whole read is a pattern you could name in one sentence.
- **Art for an emitted box wants to be UNIFORM along one axis, and that is worth prompting for explicitly.** `FacilityGeom.face`/`cap` take ONE period for both axes, so on a thin bar `v` is a narrow horizontal SLICE of the image at an arbitrary offset — a different one on the sides (`y/t`) than on the lid (`z/t`). Ask for vertical bands with no vertical structure and every slice is identical, so the pattern lines up across the lid and both sides for free and no second period is needed (contrast [`FacilityTables.panel`](../src/render/facility/FacilityTables.hx), which needed one). Verify it: `max |row_mean − mean|` on the barrier drop is **0.010 on a mean of 0.311, 3.3%**. **Ask for "TILES SEAMLESSLY ON BOTH AXES", not for "uniform" — uniform is what you want, tiling is what makes it true, and gpt will hand you the difference.** Told only "completely uniform from top to bottom", it drew the cabinet's louvre slots with rounded ENDS a few pixels inside the top and bottom edges: a horizontal feature, therefore a seam, which landed as a plain band 10% up the box's faces and **somewhere else again on its lid**, since `cap` maps `v` to `z` where `face` maps it to `y`. A UV offset cannot fix that — it hides one seam and leaves the other, and both move with the object's world position. State that the pattern runs OFF the edges and is cut flat by them. Measured on the re-prompt: row deviation **0.00706 → 0.00150**, top and bottom rows within **0.0078** per pixel.
- **`lift` cannot do a level fit on TWO-TONE art — a material `color` can.** `lift` is a gamma, so it darkens the already-dark tone far harder than the light one: on the hazard bands (0.311 mean linear, 9.5× the asphalt) lift 1.6 took the red to **0.0276**, under the asphalt it stands over, and blew the red/white ratio from **6.8× to 13.8×** — white dashes floating with the red gone. A scalar on the material's own `color` is LINEAR, holds both the ratio and the hue, and moves only the level. Fit it live at the game camera; on two-tone art the DARK tone is what fails first.
- **ONE simple object per prop. If the idea is composite, SPLIT it and say so instead of generating it.** A prop that is several things at once — parts touching, rope through a handle, cloth draped over a box — comes back with a shattered atlas and cannot be decimated afterwards at any `error`. **Holes and lace are a SEPARATE case and no longer disqualifying**: on the corrected settings `wild/bush-bramble`, a tangle of interlocking canes with real see-through holes, came back a usable prop (16 components, largest **94.2%**, a correct radial silhouette) — but still split **2.59×**, the worst in this repo, so it can never be decimated offline and has to arrive at the budget. So holes cost you the offline route, not the prop; being several objects costs you the prop. Measured: the exit ladder (one hard object) unwraps at **1.18×** and meshopt takes 93,501 tris to 5,000; `sewer-pile-1` (rubble) **3.19×**; `sewer-pile-2` (two sacks + rope + a tarp + a broken crate) **6.8×** — it shipped undecimated at 19,712 tris with a 1024² map and *still* read as mush, because no tri budget buys back a silhouette the generator never resolved. So when the ask is composite, the answer is the split, not the job: "that is a crate + a sack + a cable coil — three props, scattered separately, one draw call each."
- **Prop ideas must be MODERN, and the word "modern" goes in the reference prompt verbatim.** The game is present-day. gpt-image defaults "sack" / "crate" / "barrel" to rustic-fantasy — that is how `sewer-pile-2` arrived as hessian, hemp rope and plank boards, which read wrong in a city sewer. Reach for present-day municipal/industrial objects (200 L steel drum, solid-walled plastic stacking crate, PVC-jacketed cable coil, tied refuse sacks, wheelie bin, traffic cone, junction cabinet, PVC pipe stack), and say **modern** in the prompt. Say **solid-walled** too where it applies: a lattice milk crate is all holes, which is the failure above.
- **Paint the reference MID-VALUE. A near-black subject comes back with a hallucinated albedo, and no seed fixes it.** TRELLIS decomposes the reference into albedo + lighting; where the subject is nearly black it reads the darkness as *shadow* and lifts the base colour, hue and all. `sewer/bags` (black refuse sacks, reference luma p05 30) baked at mean sRGB **77/62/99** — violet, from a cool 68/72/77 reference — while the drum, crates and cable of the same batch (p05 35-45) all came back correct. Regenerating on a fresh seed made it *worse* (mean 110/89/114, bimodal pink-on-black). **Repainting the reference is what actually fixed it**: the same subject at mid charcoal (subject p05 30 → 48) came back at 67/70/78, cool and neutral, tracking the reference's own hue. So aim a dark prop at mid charcoal (~`#3a3d42`) and let `baseColor` darken it in the bake — that direction works, the other does not. **`#3a3d42` is a FLOOR for the darkest pixels, not a target for the whole subject** — aiming the *whole* plant there put `wild/bush-bramble`'s reference at subject luma p50 53 and it baked at 24/23/21, half the prop family. The references that bake correctly sit at **subject p50 69-77** (conifer 69 → 54/58/50; the gappy bush 77 → 84/109/61). Measure the reference before spending on it. `baseColorFactor` is a LINEAR per-channel multiply: it can drop the level and even neutralise a cast, but it can never recover a channel the generator threw away — for the other direction there is now `lift` (below), a gamma on the map. Also: TRELLIS is **not bit-deterministic** — the same seed and inputs re-ran 4,769 tris as 4,627, so a seed reproduces the look, not the file.
- **The reference is archived beside the model as `<label>-src.png`**, automatically by `image_to_3d` — a mesh cannot be regenerated or re-judged without the image it came from, and the gpt output dir is scratch. The `-src` suffix is load-bearing: `models.mjs` treats a bare `<label>.png` as a `texSrc` base-colour OVERRIDE, so archiving the reference under that name would silently repaint the prop.

## Generation settings, topology and decimation

- **`remesh_project` and `mesh_cluster` are the two knobs that decide topology, and the API defaults for both are wrong.** `remesh_project` snaps the dual-contour remesh back onto the generated surface; the API defaults it to **0** (no snap-back at all, so the prop arrives rounded off). `mesh_cluster` reaches that same remesh — not just the UV atlas, which is what its name suggests and what got it dismissed once — so its `smoothStrength` and `thresholdConeHalfAngleRad` change surface CONNECTIVITY. `image_to_3d` now defaults both to the web playground's values (**0.9**, and `{globalIterations:1, refineIterations:0, smoothStrength:1, thresholdConeHalfAngleRad:PI/2}`), so just omit them. `remesh_project`'s wire range is `(0, 1]` — a literal `0` is rejected, omit instead. **These two are worth $0.01 to re-run before any repaint**: on one gappy reference they moved it from 96 components / 24.3% largest to **1 / 100%**. A prop that came back mushy or shattered and was blamed on the tri budget or the art was really this.
- **Count a prop's CONNECTED COMPONENTS before wiring it in — the split ratio cannot see "mostly empty".** Union-find over triangle edges keyed on **unique positions**: split ratio describes the ATLAS, components describe the SURFACE, and a prop can look fine by every number already measured while being a cloud of disconnected blobs. Measured: `rock-boulder` **1 / 100%**, `bush-low` **8 / 98.7%**, `tree-broadleaf-full` **17 / 93.9%**, a retired bush **96 / 24.3%** — that last one had the same bbox and unique-position count as its replacement, so nothing else would have flagged it. Read the gate as **few components, each holding a substantial share**, not as a raw count: the shipped conifer is 2 at 51/49 (canopy plus trunk) and `tree-broadleaf-full`'s 16 extras are specks sharing 6.1%. What fails is a *largest share* under ~90%.
- **Keep a high-target master in `models-src/`, and generate the game source separately.** `models-src/` holds sources and a pre-crushed one cannot be recovered, so archive `<label>-100k.glb` (same idiom as the existing `street-lamp-raw.glb` / `street-lamp-100k/`). But for a subject meshopt cannot decimate — see the split-ratio bullet — the file `models.json` points at has to arrive at the game budget already, so generate it with `decimation_target` set to that budget and `"tris": -1`. Runware unwraps and bakes *after* its own decimation, so its output is clean at any target.
- **The split ratio predicts the LANDING POINT, and ~2× is the line between the two workflows.** meshopt never hits the `tris` target on a TRELLIS export; the seam network floors it, and where that floor sits is what the ratio tells you. Measured on one batch of four, all asked for 1200: drum (1.31×) → **4,826**, crates (1.96×) → **23,926**, cable (2.10×) → **30,431**, bags (12.1×) → undecimatable. So judge against the prop budget, not the target: **below ~1.5× the 100k-master-plus-offline-decimate route works** and lands on a normal prop (4,826; the exit ladder ships at 5,000). **At ~2× and above it does not**, and that subject has to be regenerated with `decimation_target` at the budget.
- **But the ratio is measured on the MASTER, and it says nothing about what the decimation does to the atlas — so RE-MEASURE THE BUILT GLB, and treat a blurry or smeared prop as this until proven otherwise.** Two props have now shipped on a comfortable master ratio and come back wrong: `facility/trash-bin`'s master read 1.30× and meshopt floored at 9,277 tris (twice the budget, for a cylinder) whose built atlas measured **3.86×**, and `facility/car`'s master read **1.47×** — inside the band above — while the 7,583-tri output it produced measured **2.68×** and was reported from the game as the texture having "become quite shit". Generated at budget instead, the same reference came back at **1.65×** and clean, because Runware unwraps and bakes AFTER its own decimation: the atlas is authored FOR the shipped tri count rather than being a 95k atlas dragged down with the mesh. So `tris: -1` plus `decimation_target` at the budget is the DEFAULT for anything organic or hollow, and the offline route is for hard-surfaced subjects that have been re-measured after the build.
- **Check how the subject unwraps before choosing the bake — vertex count over UNIQUE POSITION count.** meshopt cannot collapse an edge across an attribute discontinuity, so the split ratio predicts everything. The exit ladder: 55,080 verts over 46,778 positions = **1.18×**, large clean charts, and meshopt took it 93,501 → 5,000 exactly. The rubble piles: 130,974 over 41,042 = **3.19×** and 201,441 over 29,452 = **6.8×** — near-per-triangle charts, an attribute break on every edge. A hard-surfaced subject (ladder, pipe, crate) unwraps cleanly; a crumpled organic one (rubble, sacks, cloth) does not, because curvature everywhere means charts everywhere.
- **`error` does not unlock a shattered atlas — but on a CLEAN one it is worth a sweep.** On the 96k pile-1 source (3.19×): 0.005 → 54,718, 0.02 → 52,252, **0.30 → 52,184** — 60× the default cap for the same answer, and `meshCluster` at 16 global / 8 refine iterations moved 3.19× to 3.15×. Do not spend money re-generating to chase that. (That last number is about the ATLAS and does not contradict the connectivity result above: cranking the *iteration counts* barely moves the split ratio, while `smoothStrength` / `thresholdConeHalfAngleRad` at the playground values are what took a mesh from 96 components to 1. Different fields, different effect.) The trap is generalising it: swept on the low-ratio drum (1.31×) the same knob went 4,826 → 3,762 → 3,476 → **3,294** (asymptote by 0.1), a real **−32%**, while crates (1.96×) moved only −8% and cable (2.10×) −16%. So: sweep `error` before accepting a clean subject's tri count; do not bother on a shattered one.

## Texture density

- **`tex` is NOT a free knob, and getting it wrong looks exactly like a bad mesh. Always divide it by the tri count: TEXELS PER TRIANGLE.** A TRELLIS 2048 export is authored at ~43 (96,971 tris over 4.2M texels). The first pile shipped at 4,673 tris / `tex: 256` = **14**, and every crack line and grain speckle in the source was gone — read as smooth flat shards, which is what "looks like garbage" meant. `tex` was not shrinking the map, it was deleting it. Hold the ratio near the source's: 4,821 tris wants `tex: 512` (51), 19,223 tris wants `tex: 1024` (52).
- **But texels/tri is a FLOOR, not a target, and on a `tris: -1` prop it is blind to blur.** That ratio was fitted to the decimate-a-100k-master route, where the atlas and the tri count shrink together. A prop generated AT the budget has no such coupling: Runware bakes a **2048 atlas for a ~4.9k-tri mesh**, about **862 texels/tri at source**, so `tex: 512` throws away ~16x the texels while still reporting a healthy 53/tri. What catches it is **TEXELS PER WORLD UNIT** — the UV area in texels over the world triangle area, `sqrt` of the ratio, area-weighted over the mesh AT THE `h` THE GAME DRAWS IT. Measured: `tree-broadleaf-full` at `tex: 512` is **25/unit** over 292 u² of canopy, against ground/walkway/lawn tiling at 512/`GROUND_TILE` 9.0 = **57** and the grass tuft sprite at **171** — so the biggest prop in the park was the softest thing in the frame, reported as "blurry compared to grass/ground/walkway". `tex: 1024` puts it at **49**. The ground never has this problem because it TILES, so its density is constant however large the surface; a prop's atlas is finite and spread over the whole model, so density falls as the prop grows. **Check the big props, not the small ones** — `bush-low` at h 1.1 measures 108/unit and is already sharper than the ground. **And it is not only the decimate route that decouples them: a HOLLOW prop spends half its atlas on a surface nobody sees.** `facility/car` came back as an outer shell plus a cabin floor, a greenhouse interior and a bulkhead, so 9,773 tris carry **221.8 u² of skin** for a car showing about half of it — `tex: 512` would have reported a healthy 27 texels/tri and measured ~29/unit against the ground's 57. `tex: 1024` puts it at **58.7**. Measure the density, never the ratio, on anything bigger than a bush.
- **THE PIPELINE WAS DELETING COLOUR BY POLICY, in three places at once, and the fix is three lines in three files.** Reported from the game as "almost no colour in the resulting models and textures". Measured across all 38 shipped props: **17 ship with a channel spread under 2**, i.e. functionally grey, and the losses are not subtle — `wild/tree-broadleaf-full` bakes a **41.5**-chroma green canopy and ships at **3.8**, `facility/trash-bin` a bottle-green body at 20.1 and ships at **0.1**, `facility/fence-park` 23.7 → **0.4**. The three causes, each confirmed: **(1) the reference prompt.** `textures.json`'s `style` says "very dark and muted desaturated palette, low contrast" and four files mandated appending it to every gen, reference images included — correct for a wall, wrong for an object. There is now a second string, **`style_prop`**, identical but for that clause; it is what a reference takes. **(2) the `baseColor` fit.** Shipped sRGB chroma is atlas chroma × `f`^(1/2.2) — verified on three props to within 0.1 (trolley 16.2 × 0.21^0.4545 = 8.0, measured 8.0) — and **9 of 38 props carry a PER-CHANNEL factor, which is a neutraliser by construction**: it drives every channel onto one number. On a genuinely coloured bake it does not even return a legal factor (`facility/gas-cylinders`' amber asks for a **blue factor of 2.7**). `propstat` now suggests the FLAT scalar and offers the per-channel form only where there is under 8 chroma to lose. **(3) reading the family as an RGB target.** 46-52 is a **LUMA** band and says nothing about chroma — `facility/lot-cone` is luma 47 with spread 45 — so `propstat` now prints a `chroma` line beside it and labels the band as luma.
- **Pick a prop's accent hue AGAINST the light, and treat the LAMP as most of the colour in the frame.** The compound is lit by `FacilityScene`'s ambient `0x46536b`, hemisphere `0x56668c` and moon `0x8294c0` — all strongly blue — so a near-neutral albedo simply wears the light's hue. Measured: `facility/floor-tile`'s texture carries chroma **3.2** and renders at **18.3**; the grey cylinder rack's albedo carried **0.7** and rendered **7.7**. Both numbers are the lamp. Blue was the first hue asked for on that rack and would have been the one hue that cannot read here; amber sits opposite the light and rendered at chroma **101**.
- **A prop's value target is the SURFACE IT STANDS ON, and 46-52 is the outdoor one.** After the interior repaint the room floor's albedo is 95 and the wall's 111, so an indoor prop at 49 renders as a hole — measured, the trolley's shelf top came in at luma **13.9** against the generator's own bench tops at 16.1 and the floor's 86. Both kit props were refitted to **78** (`baseColor` 0.17 → 0.65 and 0.21 → 0.60). **And the response is not linear, because ACES has a toe**: raising albedo 1.6x lifted the rack's rendered luma **17.7 → 67.3**, a factor of 3.8, because the 46-52 family sits deep in the crush. Fit an indoor prop live at the game camera; do not predict it from the albedo.
- **A per-channel `baseColor` is only right when the cast it corrects belongs to the WHOLE surface. When it belongs to one material, use a FLAT scalar.** `propstat`'s suggested factor neutralises the mesh's MEAN, which is the right answer for a prop whose bake is uniformly warm or green — the bench, the railing, the bin. It is the wrong answer when the generator shifted one material and not another: `facility/car` baked TEAL on the body (atlas 60/91/104 from a near-neutral 70/73/76 reference) and near-neutral on the dark glazing, so the suggested `[0.65, 0.27, 0.2]` corrected the body and warmed the glass by the same 2.4× R-to-G ratio — **every windscreen came out rust brown**, seen from the game camera and invisible in any number `propstat` prints. A flat scalar (0.40 there) holds the hue everywhere and moves only the level. Same shape as the `lift`-vs-`color` rule below: when two tones must keep their relationship, the correction has to be the one that cannot change it.
- **Anisotropy was ruled out first and is NOT this — but glb textures were missing it.** `Textures.loadTexture` sets `anisotropy = 4` on everything the game loads by hand; `GLTFLoader` leaves every texture it makes at **1**, so props were the one thing in the frame unfiltered. Fixed via `RenderConfig.MODEL_ANISO` in `Models.get`. It is correct and free, but measure before believing it fixes a blur: in a frozen A/B (`ANIM_SPEED = 0`, HUD masked) forcing 1 → 4 moved **0.25%** of pixels by more than 2, where `tex` 512 → 1024 on the same pose moved **2.98%** — twelve times the effect.

## Materials

- **Do NOT bake a TRELLIS atlas down to vertex colours.** Tried and reverted. The reasoning that killed it: the atlas looks like a mosaic of tiny patches, but the split ratio proves it is not per-triangle (130,974 verts is 1.36× the tri count; a true per-triangle atlas would be 3×), and each patch carries real sub-triangle detail — crack lines, grain, per-face colour. `COLOR_0` throws all of it away and the prop reads as smooth white shards. Two traps found on the way, worth knowing if it is ever right for a genuinely flat-shaded prop: sample the triangle's UV **centroid** (a vertex UV sits on a chart corner = the gutter, so it reads padding and bakes near-black), and `COLOR_0` is **LINEAR** while a baseColorTexture is sRGB.
- **`Models.instanced` keeps only the FIRST mesh of a glb** and drops the rest silently — `image_to_3d` returns `meshCount` so a multi-mesh drop is visible at generation time. TRELLIS normally emits one.
- **Never enable Draco.** `Models.get` builds a bare `GLTFLoader` with no `DRACOLoader`, so a Draco glb fails to load behind a `console.warn` and the prop is simply invisible.
- **A prop dense enough to OCCLUDE ITSELF bakes that occlusion into its albedo, and `baseColor` cannot undo it — that is what `lift` is for.** TRELLIS splits the reference into albedo + lighting, and a tangle, lace or dense canopy hands it self-shadowing it cannot tell from base colour. Measured: from the same reference value a conifer bakes at **0.79×** and `wild/bush-bramble` at **0.44×**, landing on 30/29/29 against the prop family's 46-52. Neither existing route reaches it — `baseColorFactor` is a factor in `[0,1]` and only multiplies DOWN, and repainting the reference tracks *proportionally* (the same image at subject p50 53 baked 24/23/21, lifted to p50 68 baked 30/29/29: 28% brighter reference, 29% brighter bake), so hitting 46-52 that way needs a reference brighter than the `#5a5d63` backdrop it must be segmented against. So the fix is `"lift"` in `models.json`: a gamma on the base-colour MAP, `out = (v/255)**lift`, `<1` brightens. Same name and meaning as `textures.json`'s. `lift` 0.78 put the bramble at **48/47/47**. Fit it by arithmetic off the measured bake, then re-measure the built glb — the whole-atlas mean and the tri-centroid-sampled mean should agree.
- **A prop does NOT draw with the material its glb ships.** `Models.toLambert` swaps every loaded glb material for a `MeshLambertMaterial` (map, normal, ao, emissive carried over) — the same flat material every ground, wall and roof in the game already uses, because the night art has no specular in it. **The exception is the switch: a glb whose `roughnessFactor` is under 1 keeps `MeshStandardMaterial`**, and `models.json`'s `roughness` dial is what bakes that — so `roughness` now means "this prop wants a specular highlight, keep it on the PBR path" (the habitat props, 0.30-0.45; the hangar ship at 0.80 and the corp glbs at 0.72 keep it on look). **The Blender lib bakes 0.72 into EVERY hand-modelled glb** (`models-src/facility/buildlib.py`, `bsdf Roughness`), which silently sent 54 facility, wild and scenario-a props back to PBR — so a hand-modelled prop meant for Lambert carries `"roughness": 1` in `models.json`. Measured on the Radeon: park GPU 7.3 → 4.7 ms. For every other prop the MR map is never sampled, which makes `dropMR` a no-op and takes a metallic-1 bake off the table as a bug class. **Why it is not just hygiene: it was the single biggest render win in the facility.** A TRELLIS prop is ~5k tris over a 40-pixel silhouette, so its triangles are SUB-PIXEL, the fragment shader runs once per 2x2 quad however small they get, and prop cost therefore tracks TRIANGLES and barely moves with resolution. Measured on the integrated Radeon, park in frame, 3.6M tris at 1080p: **31.4ms → 20.3ms GPU (32 → 49fps)**; culled follow view 8.99 → 6.58. Full numbers in `docs/3d-changes.md`.
- **A generated PBR export lands at metallic 1 / roughness 1 with an MR map.** That is not automatically wrong — the exit ladder's reads correctly as dark metal and had `dropMR`/`baseColor` reverted. `dropMR` + `baseColor` in `models.json` are the fix if it really does read as chrome, not shader work. **Both are now dead letters for any prop on the Lambert path (above); they still apply to a `roughness`-dialled one.**
- **Read the MR map itself before guessing — it is one image and it answers the question outright.** glTF packs **G = roughness, B = metalness**, so a dump of the baked texture is decisive: `sewer-pile-1` came out pure green (rough dielectric, correct) and `sewer-pile-2` came out **cyan** — metalness 1 across sacks, wood and cloth alike. That one needed `dropMR`; its neighbour, from the same generator on the same day, did not. **A uniformly metallic prop renders BLACK under debug key `1`**, not chrome: WYSIWYG hides every light, a metal has no diffuse term, and with no analytic light and no env map there is nothing left to shade. So key `1` showing a black prop is the metalness tell, and `M` confirms it.
- **A PROP'S LEVEL DRIFTS, AND NOTHING WATCHED IT UNTIL NOW: `python3 tools/propstat.py --audit $(find app/models -name '*.glb')` is the register.** One line per built glb, sorted by shipped luma, with the chroma beside it and the `baseColor` factor named where there is one. Reach for it whenever a prop is reported as bright, dark or loud, and read it again after fitting one — this is a whole-family judgement and there is no such thing as fixing a single prop's value. Four things it exists to say:
  - **The atlas is NOT the shipped pixel.** `sat` and `lift` bake into the built map, but `baseColor` is a **linear multiply applied at render**, and nine props carry one. `propstat` ignored it for its whole life, which is why every `models.json` value note had to redo the arithmetic by hand, and why three of them then drifted: `facility/desk-mug` read 185 in the atlas while shipping 122. It folds the factor in now, in linear light, and prints `THROUGH baseColor …` when it does. **0.4 on 185 is 74 in bytes and 122 in light** — reading one for the other is how a fit lands 50 points out.
  - **A CELL MEAN is not what a prop wears either.** A hand-modelled prop maps narrow WINDOWS of its sheet's cells (`facility/deco-shelving`'s uprights are columns 4..31 of cell 0), so the three cells of `store-sheet.png` measuring 54.7 / 73.5 / 77.5 says nothing about a unit that samples 93. Only the UV-sampled number is honest, and `--audit` is the only place it is written down.
  - **Two bands, and both are read against the NEIGHBOURS: 46-52 outdoors, ~78 indoors** (the repainted interior is floor 95, wall 111). Every report that produced this register was a prop that had drifted off the props *beside* it, never off an absolute: a cup at luma 126 was defended as "the lightest thing on the desk" against a laminate at 94.7, and 126/94.7 is 1.33× in bytes and **2.1× in light**, which is not a white mug, it is a lamp.
  - **A sheet shared between a prop's OWN surfaces needs a rect, not a knob — `gradeRect` in `models.json`.** `lift`/`sat`/`baseColor` are per LABEL, and `facility/desk-tray` carries a paper sheaf at 165.6 in a tray body at 59.6 off one map: the gamma that brings the paper to 95 takes the body to 10. `gradeRect` is `[{ "rect": [x0,x1,y0,y1], "scale": …, "sat": … }]` in the EMBEDDED MAP's pixels, applied to that label's own baked copy — so the number lives in the repo rather than in the unversioned asset store, and two labels off one sheet can grade the same rect differently. It is [`tools/cellgamma.py`](../tools/cellgamma.py)'s job for models, with one difference that matters: **`scale` is LINEAR and holds the rect's internal contrast.** A gamma that reached the same level on that paper took its chroma from 53 to 65 and left an ochre card.

## Making a prop glow

- **A prop that has to GLOW takes an emissive map, and on a TRELLIS atlas that map is GENERATED, not hand-painted.** `emissiveSrc` in `models.json` (+ `emissiveStrength`, default 3, HDR so bloom catches it) is the street lamp's own route and it is the right one for any fixture — a quad hung at the bulb is fixed-yaw by construction and reads as a sticker on a prop that yaws. The atlas layout being unknown is not the obstacle it looks like, and there is a tool: **[`tools/emissive.py`](../tools/emissive.py)** — `--bbox` prints the mesh frame, `--box x0,x1,y0,y1,z0,z1` selects triangles by CENTROID in that frame, and it rasterizes their UV triangles into a tinted mask (`models.mjs` pins `emissiveFactor` to `[1,1,1]`, so the hue lives in the map). **Run it on the BUILT glb, never the 100k master**, or the mask misses a chart the decimation moved. Five things it exists to enforce, each learned by shipping the mistake:
  - **Select by a BOX, not by normals.** A `NORMAL`-based "downward-facing faces" filter reads plausible and is unverifiable; a box is stated in printed coordinates and shows up in the preview.
  - **The dilation is the thing that puts glow where it does not belong.** The push into the chart gutter (needed so a resize and bilinear sampling do not read black at a chart edge) reaches the NEXT chart on a mosaic atlas, and that chart is an unrelated part of the surface. Measured on `facility/lamp-post`: **22 unselected triangles lit, from y −0.498 to +0.484 — the mast, down to the base plate.** The tool masks the dilation against every unselected triangle's coverage and **reports the bleed count; ship only at 0.**
  - **Rasterize CONSERVATIVELY, and check per TRIANGLE — a mask can measure clean and still speckle.** `PIL.ImageDraw.polygon` fills by pixel CENTRE, so a chart thinner than a texel covers *nothing at all*, and a TRELLIS atlas is full of those: invisible to the bleed mask, still sampled by the GPU. So supersample 4x and max-pool down (covered = ANY part of a triangle falls in the texel), add `outline=255` for a triangle even that misses, and grow the unselected coverage by 1 texel before subtracting, because bilinear reads a 2x2 neighbourhood. The CHECK needs the same care: testing each unselected triangle's UV *centroid* misses a triangle with one lit corner, which still draws a speck. Measured — a mask the centroid test called clean bled onto **9 triangles down the pole**.
  - **A flat mask is right for a LENS and wrong for a WINDOW RUN — that is what `--modulate` is for.** The flat mask lights every selected texel equally, which is correct for one small bright thing and is a *white card stuck on a black box* for a big region whose whole read is its structure: `facility/booth`'s glazing lit flat lost its mullions entirely, and dropping `emissiveStrength` from 2.2 to 1.1 only made the card dimmer — the halo went and the card stayed, because the failure is uniformity, not level. `--modulate` multiplies the mask by the glb's **own base-colour map**, which already separates the panes from the frames by ~3x in value, so the glow lands on the glass and the mullions stay dark for free. It costs brightness (that booth's lit texels went 255 → mean 117), so the strength goes UP to compensate — 3.5 there against a flat map's 2.2 — and only the panes then clear `BLOOM_THRESHOLD`, which is the "lit window" read rather than a lamp.
  - **Author at the entry's own `tex`** (320 for that prop), not 512: `models.mjs` resizes the emissive too, and the resize re-introduces the ramp the bleed mask just removed.
  - **`--preview` renders 3 orthographic views with the selection in red, framed ON THE SELECTION** — a lens is 2% of a 6-metre mast and is one pixel in a whole-prop view. Look at it before `make models`.
- **Where the glow goes is an ART call the camera decides, and it is not the physically-correct face.** A flat slab head lit whole reads as a glowing card, because its biggest face is the TOP and the camera looks down. The physically-right answer — the lens on the underside — is **invisible from an overhead camera**, and leaves the cone and the ground pool to carry the "it is on" read. A glow you actually want to SEE has to be on a face the camera can see, so widen the box deliberately rather than reaching for realism.

## Wiring it into the game

- **Warm every new glb path, one entry per material variant it will ever draw** (`SOLID`/`GHOST`/`HULL` each compile their own program). Instanced beside the rest of the warm scene it lands after `compileAsync` has walked it and compiles on first area entry instead. **The list is NOT in `View.hx` any more** — that file only routes a warm per area kind (`View.warmKind`); the facility's rows are `FacilityWarm.facProps` (once per PATH — the machine appears once for its two heights) and `FacilityArea.EXTRA` (once per BATCH, index-aligned with `green`, so the machine appears twice there).
